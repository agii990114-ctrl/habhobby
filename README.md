# HabHobby

흩어진 미디어 생활을 하나의 목록으로. 웹툰·드라마·영화·애니를 어느 플랫폼에서 보든
한 곳에서 이어 보는 **통합 미디어 런처**.

기록 앱이 아니라 런처다. "몇 화까지 봤는지"는 각 플랫폼의 이어보기가 이미 알고 있으므로
중복해서 관리하지 않는다. 우리가 하는 일은 **흩어진 최근 본 목록들을 한 화면에 모으고,
누르면 그 플랫폼으로 되돌려보내는 것**이다.

## 빠른 시작

```bash
npm start         # http://localhost:8080
```

의존성이 없다. Node 22.18+ 의 TypeScript 직접 실행과 내장 `node:sqlite` 만 쓴다.
`npm install` 도 빌드 단계도 필요 없다.

| 명령 | 하는 일 |
| --- | --- |
| `npm start` | 서버 (API + 정적 파일 + 공유 대상) |
| `npm run reset` | DB 삭제 (데이터 전부 사라짐) |

## 설계 원칙

이 네 가지가 서비스의 전부다.

**P1 · 등록은 공유 버튼으로.** 플랫폼 공식 API는 존재하지 않는다. 각 앱의 공유 시트에서
HabHobby를 고르는 탭 한 번이 등록의 전부다. 계정 연동도, 로그인 세션 수집도 없고,
사이트가 공개한 링크 미리보기 정보(Open Graph) 외에는 아무것도 가져오지 않는다.

**P2 · 연결은 시리즈 단위로.** 보던 화가 아니라 작품의 회차 목록으로 되돌려보낸다.
공유 URL에서 시리즈 ID만 뽑아 목록 주소로 재조립하므로 회차 주소보다 안정적이다.

**P3 · 진행도는 플랫폼에 위임.** 대부분의 플랫폼이 이어보기를 제공한다. 목록 페이지로
보내주면 "16화 이어보기"는 플랫폼이 알아서 띄운다.

**P4 · 커버리지는 고르지 않다.** 플랫폼마다 얻을 수 있는 정보가 다르고 시간이 지나면
그마저 바뀐다. 고칠 결함이 아니라 전제다. **모든 기능은 "그 정보가 없는 상태"를
정상 동작으로 갖는다** — 규칙 없는 URL은 도메인 묶음으로, 일정 없는 작품은 "일정 없음"으로.

## 구조

```
src/
  db.ts          SQLite 스키마와 접근 계층 (node:sqlite) — 모든 데이터가 user_id로 격리
  auth.ts        카카오·네이버·구글 OAuth + 세션
  platforms.ts   URL 규칙 — 플랫폼 추가는 이 배열에 한 줄. 네트워크를 쓰지 않는다
  resolve.ts     URL → 제목·표지 (Open Graph)
  server.ts      HTTP: API + 정적 + 공유 대상
public/          앱 (의존성 없는 ES 모듈)
data/            SQLite 파일 — 내 작품만 들어 있다
```

### 정보를 얻는 경로는 하나뿐이다

**Open Graph 태그.** 사이트가 `<head>`에 "이 페이지를 소개할 땐 이 제목과 이 그림을 써달라"고
스스로 공개해 둔 메타데이터다. 카카오톡·슬랙의 링크 미리보기가 읽는 바로 그것이다.

```html
<meta property="og:title" content="화산귀환">
<meta property="og:image" content="https://shared-comic.pstatic.net/…">
```

**플랫폼의 비공개 내부 엔드포인트는 쓰지 않는다.** 그건 각 사이트가 자기 화면을 그리려고
만든 통로이지 제3자더러 쓰라고 연 것이 아니고, 남의 연재 목록을 통째로 복제해 두는 일이
되기 때문이다. 그래서 이 프로젝트는 **자기 DB에 남의 목록을 저장하지 않는다** — `data/` 에는
사용자가 직접 등록한 작품만 들어 있다.

대가는 하나다. **연재 요일은 자동으로 채워지지 않는다.** OG 규격에 그런 항목이 없다.
등록할 때 사용자가 요일을 고르고, 작품당 한 번이면 끝난다.

### 플랫폼별 결과 (실측)

방식은 전 플랫폼이 동일하다. 결과가 다른 것은 **사이트가 얼마나 성실히 공개했는가**의 차이다.

| 플랫폼 | 제목 | 표지 | 앱으로 열기 |
| --- | --- | --- | --- |
| 네이버웹툰 · 카카오웹툰 · 라프텔 | 자동 | 자동 | 가능 |
| 네이버시리즈 · 리디 · 넷플릭스 | 자동 | 자동 | 가능 |
| 네이버 블로그 | 자동 | 없음 | 가능 |
| 카카오페이지 · 티빙 | 직접 입력 | 일부 | 가능 |
| URL 규칙이 없는 모든 도메인 | 사이트에 따라 | 사이트에 따라 | 웹으로 |

연재 주기는 **전 플랫폼 사용자 지정**이다. 고를 수 있는 것:

| 주기 | 고르는 것 | 저장 |
|---|---|---|
| 매주 | 요일(복수) | `days` = 요일 0~6 |
| 격주 | 요일(복수) + 기준 주 | `days` + `next` = 기준 주의 월요일 |
| 매월 · 날짜로 | 날짜(복수, 1~31) | `days` = 날짜 |
| 매월 · 요일로 | 주차 × 요일(복수) | `days` = `주차<<3 \| 요일` |
| 날짜 지정 | 하루 | `next` |
| 상시 · 완결 · 휴재 · 미정 | — | — |

`days`는 주기에 따라 뜻이 다르므로(요일 ↔ 날짜) 모드를 갈아탈 때 비운다.
매월 31일처럼 **그 달에 없는 날짜는 말일로 당겨** 놓는다 — 건너뛰면 한 달이 통째로 빈다.

**매월은 두 가지로 말할 수 있다.** "매월 15일" 처럼 날짜로도, "매월 둘째 화요일" 처럼
주차와 요일로도 정한다 — 후자가 실제 연재에서 흔하다. 모드 버튼은 `매월` 하나로 두고
그 안에서 **날짜로 / 요일로** 를 고른다. 저장은 각각 `monthly` 와 `monthly-dow` 로 갈린다.

주차 × 요일은 한 숫자에 담는다(`주차<<3 | 요일`). 요일이 8보다 작으므로 자리를 나눠 쓰면
섞이지 않는다. 주차 5는 **마지막** 을 뜻하고, 그 요일이 네 번뿐인 달에는 네 번째에 놓인다 —
2026년 1월의 마지막 금요일은 30일, 2월은 27일이다.

반복 일정은 **정한 시점부터** 적용된다. 월요일에 수요일 연재를 등록하면 이번 주 수요일부터
놓이고, 지난 수요일들에는 놓이지 않는다 — 그때는 목록에 있지도 않았다. 기준은 `sched_from`
이고, 일정을 고칠 때마다 그 시점으로 갱신된다. 값이 없는 예전 행은 `added_at` 으로 대신한다.

## 주소 없이 담기

주소가 늘 있는 건 아니다. **개봉을 기다리는 영화**는 아직 페이지가 없고, 그런 것도 캘린더에
올려두고 싶다. ＋ → **직접 입력** 으로 제목과 날짜만 넣으면 된다.

이런 항목은 `note` 플랫폼("직접 입력")에 모인다. `hosts` 가 비어 있어 어떤 주소에도 걸리지
않고, 오직 직접 만들 때만 쓰인다. `list_url` 은 빈 문자열이고, 작품 화면에서는 **보러가기가
사라지고** 대신 어떻게 된 항목인지 알려준다.

나중에 페이지가 생기면 작품 설정에서 **주소를 붙일 수 있다.** 주소가 붙으면 제목·표지·플랫폼을
다시 얻어야 하므로 새로 담고 옛 항목을 지우되, **일정과 폴더는 그대로 옮긴다** — 사용자가
이미 정해 둔 것이다.

## 공유받은 문자열에서 주소 골라내기

공유 버튼이 주소만 보내주지 않는다. 네이버웹툰은 이렇게 보낸다:

```
[네이버 웹툰] 청부입학
https://naver.me/G9UVxdoU
```

그래서 `parseShared` 는 먼저 **문장 속에서 `http(s)://` 로 시작하는 조각을 골라낸다**
(`extractUrl`). 없으면 입력 전체를 주소로 본다 — 스킴 없이 도메인만 친 경우를 위해서다.
문장 끝에 붙은 마침표·따옴표는 떼되 **괄호는 두 손 뗀다** — 위키백과 주소처럼 실제로 쓰인다.

주소를 고르는 일은 **단축 주소를 풀기 전에** 해야 한다. 제목이 붙은 문자열은 URL 로 읽히지
않아서, 그대로는 `naver.me` 가 단축 주소인지조차 알아볼 수 없다.

## 도메인 묶는 기준

**호스트 하나가 구간 하나다.** `music.apple.com` 과 `books.apple.com` 은 따로 남고,
`product.kyobobook.co.kr` 과 `event.kyobobook.co.kr` 도 따로 남는다. `www.` 와 `m.` 만
같은 곳으로 본다.

자동으로 합치지 않는 이유는 **이름의 기준이 어긋나기 때문**이다. 사이트가 밝히는 이름은
그 호스트의 것이라, `music.apple.com` 을 `apple.com` 으로 합치면 "Apple Music" 인지 "Apple"
인지가 **어느 주소를 먼저 넣었는지**에 달리게 된다.

합치는 판단은 사용자가 한다. 구간 이름을 치는 동안 **비슷한 이름의 구간이 목록으로** 뜨고
(이름 일부든 주소 일부든 걸린다 — "교보문고" 로도 "kyobo" 로도 찾힌다), 하나를 고르면
이름이 채워지면서 **"그 이름의 구간이 이미 있습니다 · 한 단락으로 합치기"** 로 바뀐다. 누르면
작품이 옮겨가고, 그 판단은 `domainMerges` 에 남아 **다음에 그 사이트에서 추가해도 같은 자리로**
들어간다.

합칠 때 **"앞으로 `*.kyobobook.co.kr` 도 전부 여기로"** 를 켜면 그 등록 단위 아래 형제 구간이
한꺼번에 오고, 나중에 생기는 하위 도메인도 자동으로 따라온다(`domainMergeWild`). 꺼두면
그 호스트 하나만 옮긴다 — 말한 것보다 많이 하지 않는 쪽이 기본이다.

**떼어내기**도 있다. 구간 편집의 "담긴 주소" 에서 호스트를 골라 떼면 그 주소의 작품만 나가고,
`domainMerges` 에 자기 자신을 가리키는 항목이 생겨 도메인 규칙이 다시 끌어가지 못한다.
이름은 그 호스트의 대문에서 **새로 받아온다** — 합쳐질 때 지워졌으므로 그냥 두면 주소만
남는다. 부모와 같은 이름이 나올 수도 있지만, 일부러 떼어낸 것이니 그건 사용자가 고칠 일이고
이름이 없는 것보다 낫다. 대문을 못 읽으면 표시를 남기지 않아 나중에 다시 묻는다.

모든 판단은 서버에 남아 다시 켜도 유지된다.

`registrableDomain()` 과 `MULTI_SUFFIXES`(co.kr·co.jp 등 130여 개)는 구간을 나누는 데는
쓰지 않는다. 사이트 이름을 고를 때 "brunch.co.kr 의 핵심 낱말은 brunch" 를 알아내는
힌트로만 쓴다.

## 도메인 구간의 이름

규칙에 없는 사이트는 **도메인별로 한 묶음**이 된다. 그 묶음의 이름은 사이트가 스스로 밝힌
**`og:site_name`** 을 쓴다 — 제목·표지와 같은 경로다. `github.com` 은 "GitHub", `namu.wiki` 는
"나무위키" 로 보이고, 마크도 그 첫 글자가 된다.

| 순위 | 값 |
|---|---|
| 1 | 사용자가 직접 지은 이름 (✏️ 편집) |
| 2 | 사이트가 밝힌 `og:site_name` |
| 3 | 도메인 주소 그대로 |

작품을 새로 넣을 때 함께 얻고, **이미 쌓여 있던 도메인은 앱을 열 때 여섯 개씩** 뒤늦게 채운다
(`POST /api/platforms/site-names`). 한 사이트당 한 번이면 되므로 결과는 못 얻은 경우까지
기억한다 — 안 그러면 같은 사이트를 열 때마다 두드린다.

이름은 **글 페이지가 아니라 도메인 홈페이지에만 묻는다.** 한때 작품을 담을 때 그 페이지가
밝힌 `og:site_name` 을 함께 썼는데(요청 한 번을 아끼려고), 교보문고 전자책 페이지가
**IMDb** 라고 답하는 일이 있었다 — 영화 〈더 록〉의 IMDb 메타 태그가 통째로 붙어 있었고
교보는 자기 `og:site_name` 을 넣지 않아 그 값만 남아 있었다. 한 페이지의 실수가 사이트 전체
이름이 되는 구조라 지름길을 없앴다. 사이트가 스스로를 뭐라 부르는지는
대문에 적혀 있고, 글 페이지만 봇을 막아 둔 곳도 많다 (브런치가 그렇다).

홈페이지에서 `og:site_name` 이 있으면 그것을, 없으면 **제목의 앞부분**을 쓴다 —
"Hugging Face – The AI community building the future" 는 첫 구분자에서 잘라 "Hugging Face" 가
된다. 표어가 앞에 오는 사이트도 있어서, 도메인과 같은 조각이 있으면 그쪽을 먼저 믿는다.
잘라내고도 24자를 넘으면 이름이 아니라 문장을 집은 것으로 보고 버린다.

실측 10곳 중 8곳에서 이름을 얻는다 (`Hugging Face` · `위키백과` · `Hacker News` · `velog` ·
`브런치` · `GitHub` · `MDN Web Docs` · `나무위키`). 못 얻는 둘은 봇을 막는 스택오버플로와,
제목이 `arXiv.org e-Print archive` 라 문장으로 걸러지는 arXiv 다. `application-name` 과
웹 매니페스트도 재봤지만 열 곳 모두 0이라 넣지 않았다 — 안 도는 기계다.

못 얻는 경우는 둘이고 화면에서 구분해 알린다. **읽었는데 이름이 없는 곳**(위키백과)과
**아예 못 읽는 곳**(봇을 막는 사이트)이다. 뒤엣것은 나중에 되기도 하므로 편집 화면의
**사이트에서 가져오기**로 다시 물어볼 수 있고, 다른 작품을 그 사이트에서 추가할 때도 저절로 낫는다.

### 마크 글자색

마크(목록에 붙는 한두 글자)의 글자색은 배경색에서 대비를 재어 흰색과 검정 중에 고른다
(`readableOn`). 다만 경계에 걸친 색에서는 계산이 고른 쪽이 눈에 안 들 때가 있어
**표시 설정에서 직접 고를 수도 있다** — `자동 · 흰색 · 검정`.

직접 고른 값만 `overrides.fg` 에 남는다. "자동" 이면 그 칸이 비고, 배경색을 바꾸면 글자색도
따라 바뀐다. 반대로 한 번 고르고 나면 배경을 바꿔도 고른 값이 그대로다 — 그러라고 고른 것이다.
서버는 흰색·검정 두 값만 받는다.

## 캘린더

**주간**과 **월간** 두 가지로 본다. 달력 위 버튼으로 오갈 수 있고, 보기 설정은 화면 상태라
서버에 저장하지 않는다.

- **주간** — 오늘부터 이레. 요일이 열이고, 좁은 화면에서는 세로로 쌓인다.
- **월간** — 한 달을 한눈에. 칸이 좁아 제목을 못 넣으므로 플랫폼 색 점으로 요약한다.
  **날짜를 눌러야** 그 날의 목록이 열리고, ✕ 또는 같은 날을 다시 눌러 닫는다.
  `‹ ›` 로 달을 옮기며, 달을 넘기면 선택은 자연히 풀린다.

**격자에는 감상 완료한 작품도 남는다.** 등록한 날부터 완료한 날까지는 그대로 보인다 —
"언제부터 언제까지 보던 작품" 이 기록으로 남는다. 반면 **휴지통은 아예 놓지 않는다** —
관심이 없어진 것이라 기록으로 남길 이유가 없다.
흐리게, 취소선과 함께 그려서 지금 볼 것과 구분한다. 기준은 `state_at`(상태를 바꾼 시각)이고,
값이 없는 예전 행은 `last_at` 으로 대신한다.

격자 아래 단락은 앞으로 볼 것을 위한 자리라 **활성 작품만** 다룬다.

격자 아래 단락은 **여집합으로 구한다** — 격자에 놓인 것을 빼고, 남은 것을 순서대로 거른다.

| 단락 | 들어가는 것 |
|---|---|
| 공개 예정 | 날짜 지정 중 **오늘 이후**. 날짜 오름차순 |
| 상시 · 언제든 | 상시 + 완결 |

기준은 **보고 있는 달이 아니라 늘 오늘**이다. 달로 재면 4월 달력에서 7월 공개작이 "예정"으로
뜨는데, 이미 나온 작품이라 틀린 말이 된다.

이 단락들은 **격자와 무관하게 고른다.** 달을 넘기거나 날짜를 눌러도 내용이 바뀌지 않는다 —
격자에 있다는 이유로 빼면 9월을 볼 때만 9월 공개작이 목록에서 사라져, 읽는 사람이 기준을
매번 다시 세워야 한다.

## 추가 목록 — 달력에 안 보이는 것들

**공개 예정도, 일정을 안 정한 작품도 격자 아래에 늘어놓지 않는다.** 둘 다 캘린더를 밀어내기만
한다. 대신 오른쪽 아래 **아이콘**(📋 · 개수 표시)을 누르면 「추가 목록」이 열린다.

### 왜 오른쪽 아래인가

왼쪽 아래에 담기(＋)가 있으니 **같은 크기로 그 짝**을 놓았다. 둘 다 여느 아래 시트를 연다. 내려 읽을 때 함께 비켜나는
것도 같다(`.tucked`) — 목록을 읽는 동안 화면 아래를 두 개가 가리고 있을 이유가 없다.

빛깔만 다르다. 담기는 이 앱의 첫 일이라 채워 두고, 곁창은 테두리만 두른다. 둘 다 채우면
어느 쪽이 먼저인지 흐려진다. **캘린더에서만, 담을 것이 있을 때만** 나온다 — 빈 창을 여는
버튼은 눌러 볼 이유가 없다.

### 무엇이 들어 있나

두 종류를 한 창에 둔다.

「추가 목록」에는 **날짜 미지정만** 담는다 — `상시 · 완결 · 휴재 · 일정 미정`, 그리고
정하다 만 `요일 미선택 · 날짜 미선택 · 날짜 미지정`. 놓일 근거가 아예 없어 손봐야 할
목록이다.

**공개 예정은 달력 바로 아래에 제 단락으로 선다.** 한때 추가 목록에 함께 담았는데,
날짜가 있는 것들이라 달력의 이야기이지 손볼 목록이 아니다. 성격이 다른 둘을 한 창에 두면
"여기 있는 건 다 고쳐야 하나" 가 된다. 두 곳 모두 **같은 단락 모양**(`secHtml`)을 쓴다 —
가로로 훑고, ☰ 로 전부 펼친다.

**공개 예정에는 며칠 남았는지를 적는다**(`오늘 · 내일 · 12일 뒤`). 카드의 시각 자리는 본래
"언제 봤는지" 인데, 아직 안 나온 작품에는 그 말이 성립하지 않는다 — 본 적이 없기 때문이다.
날짜끼리 재므로 시각은 보지 않는다: 오늘 밤 11시와 내일 새벽 1시는 두 시간 차이지만
"오늘" 과 "내일" 이다.

둘 다 "지금 화면에는 없지만 알고 있어야 하는 것" 이라 함께 둔다. 날짜 미지정은 **왜 날짜가
없는지로** 묶는다. 앞의 넷은 저마다 색 점을 달고 정하다 만 셋은 한 색으로 묶는다 — "손봐야 할
것" 이라는 점에서 셋이 같다. 폴더로 묶으면 상시로 담은 작품이 폴더가 없다는 이유로 "미분류" 에
섞여, 정작 알고 싶은 것이 가려진다.

### 훑는 화면과 다루는 화면

단락마다 **가로로 미는 목록**이다 — 페이지 탭과 같은 모양(`.plat` · `.rail`)을 쓴다.
같은 일을 두 곳에서 다르게 보이게 할 이유가 없다. 단락 오른쪽 **☰** 를 누르면 그 단락의
전체 목록이 펼쳐지고, 줄마다 날짜·폴더·플랫폼이 붙는다.

**전체 목록은 창을 새로 띄우지 않는다.** 같은 창 안에서 내용만 갈아 끼우고 머리줄에
`‹` 를 둔다 — 곁창 위에 또 곁창이 쌓이면 어디까지 돌아가야 하는지 알 수 없다.
항목을 누르면 다른 목록과 똑같이 작품 화면이 **위에 겹쳐** 뜨고, 닫으면 곁창으로 돌아온다.
일정을 정하러 왔더라도 보러 갈 수 있어야 한다.

### 단락 — 값을 넣는 화면은 나눠 둔다

URL 추가와 직접 입력은 칸이 줄줄이 붙어 있어서 **어디까지가 한 가지 이야기인지** 알 수 없었다.
이제 단락마다 사이를 벌리고 연한 선을 긋는다(`.sep`).

| 화면 | 단락 |
|---|---|
| URL 추가 | 주소 → 플랫폼·제목 → 캘린더 점 색·연재 일정 → 폴더 → 등록 |
| 직접 입력 | 제목 → 캘린더 점 색·연재 일정 → 폴더 → 등록 |

**색과 일정은 한 단락이다** — 둘 다 달력에서 이 작품이 어떻게 보이는지를 정한다. 그래서
구분선은 둘을 감싼 바깥에 한 번만 긋는다.

선을 긋는 자리는 `schedHtml` · `pickerHtml` · `actionRow` 안에 있다. 이 셋은 작품 설정도
함께 쓰므로 **그 화면도 같이 나뉜다** — 같은 블록이 같은 차례로 쌓이는데 한쪽만 나뉘어
있으면 그게 더 이상하다.

**본문 맨 처음에만 긋지 않는다.** `:first-child` 만으로 가르면, 단락이 상자 안에 나뉘어
담기는 자리(직접 입력의 일정·폴더는 `[data-manual-body]` 안에 있다)에서 위에 다른 이야기가
있는데도 선이 지워진다. 그래서 `.sheet-body > .sep:first-child` 로 못 박았다.

> **한때 말풍선이었다.** ＋ 와 📋 의 창을 아이콘에서 피어나는 말풍선(꼬리 달린 팝오버)으로
> 만들어 두었다가, 써 보고 **여느 아래 시트로 되돌렸다.** 자리가 좁아 목록이 금세 갑갑해지고,
> 다른 창은 다 아래에서 올라오는데 둘만 옆에서 튀어나와 손이 두 가지를 기억해야 했다.
> 지금은 모든 창이 한 가지 모양이다.

**가로 목록 위에서는 끌어 내리기를 시작하지 않는다.** 옆으로 밀다 창이 닫히면 곤란해서,
글자 칸과 같은 자리에 `.rail` 을 함께 적어 두었다.

여기 담기는 기준은 **작품의 설정뿐이다.** 격자의 여집합으로 구하면, 8월 31일 월요일에
수요일 연재를 보는 순간 8월에 남은 수요일이 없어서 멀쩡한 작품이 여기로 떨어진다. 창에
안 보이는 것과 설정이 빠진 것은 다르다.

**지난 공개는 목록에 넣지 않는다.** 앞으로 볼 것이 아니면서 시간이 갈수록 쌓이기만 한다.
대신 몇 편이 빠졌는지 한 줄로 알린다 — 조용히 사라지면 "내 작품 어디 갔지"가 되기 때문이다.
격자에는 그대로 놓이므로 그 달을 열면 여전히 보인다. 이 숫자도 달을 옮겨도 변하지 않는다.

## 되돌릴 수 없는 일은 한 번 더 묻는다

지우기 · 휴지통 · 친구 끊기 · 탈퇴 · 설정 되돌리기는 **작은 창을 띄워 다시 묻는다.**
`askSure({ title, body, ok, back })` 하나가 그 창을 맡고, 부르는 쪽은 `await` 로 답을 받는다.

```js
const yes = await askSure({
  title: "폴더를 삭제할까요?",
  body: "웹툰 · 12개. 묶음만 사라지고 작품은 목록에 남습니다.",
  back: () => openFolderForm(existing, after),   // "아니오" 면 돌아갈 화면
});
if (!yes) return;
```

**한때 이 일을 버튼이 저 혼자 맡았다.** 누르면 글씨가 "정말 삭제할까요?" 로 바뀌고 한 번 더
누르면 지워지는 식이었다. 지우는 자리마다 모양이 달랐고 — 어떤 곳은 옆에 취소가 돋아나고,
어떤 곳은 글씨만 바뀌었다 — 무엇보다 **같은 자리를 두 번 누르는** 손짓이었다. 잘못 눌러
놀란 손은 대개 한 번 더 누른다. 창을 띄우면 손이 멈추고, 무엇을 몇 개 지우는지 읽게 된다.

`body` 에는 **무엇이 사라지고 무엇이 남는지**를 적는다. "정말 삭제할까요?" 만으로는
폴더를 지우면 작품까지 없어지는 줄 알고 망설이게 된다.

지우는 버튼은 **붉다**(`--bad`). 전에는 강조색을 그대로 썼는데, 그러면 저장 버튼과 같은
빛깔이라 손이 구별하지 못했다. 이 값은 테마 색을 바꿔도 따라가지 않는다 — 설정에서 만드는
것은 `--accent` 셋뿐이라(「테마 색」) 어떤 테마에서도 지우는 버튼은 붉게 남는다.

**"예" 를 고르면 창만 걷고 다음 화면은 부른 쪽이 연다.** `hideSheet()` 가 그 일을 한다 —
아래에 쌓아 둔 시트(「시트를 겹쳐 열기」)는 건드리지 않으므로, 부르는 쪽 코드는 되묻기가
없던 때와 똑같이 이어진다. "아니오" 나 배경 톡 · 끌어 내리기는 `back` 을 불러 보던 화면으로
되돌린다. `back` 을 넘기지 않으면(폴더 탭처럼 창 없이 부른 자리) 그냥 닫힌다.

## 목록에서 내리기와 별점

작품은 지워지는 대신 **감상 완료**나 **휴지통**으로 옮겨진다.

**감상 완료로 옮길 때만 별점을 묻는다.** 잘못 눌렀을 때 빠져나갈 수 있도록 **취소**가 있고,
아무것도 바꾸지 않고 작품 설정으로 돌아간다. **휴지통은 별점을 묻지 않는다** — 버리는 것에
점수를 매길 일은 없다. 대신 정말 내릴 것인지는 되묻는다(위 「되돌릴 수 없는 일은 한 번 더
묻는다」). 이미 매긴 점수는 지우지 않아, 되돌리면 그대로 살아난다. 옮길 때 **별 다섯 개 중 클릭**으로
별점을 매길 수 있고, 안 매겨도 된다 — 강요하면 내리기 자체를 망설이게 된다.
안 고르면 그만이라 건너뛰는 버튼은 두지 않았다. 이미 매긴 점수는 미리 켜져 있으므로
그냥 옮기면 그대로 남는다.

보관함은 **전체 화면 시트**로 열린다 — 목록이 길어 낮은 시트로는 좁다. 제목줄이 고정되고
본문만 스크롤되며, 배경을 눌러 닫을 수 없으므로 **닫기 버튼**이 유일한 출구다.
(`openSheet(html, { full: true, title, sub })`)

**별점별 폴더는 감상 완료에만 있다.** 휴지통은 점수를 매기지 않으므로 한 줄로 펼친다.

감상 완료에 들어가면 **별점별 폴더**가 보인다. `★★★★★` 부터 내려가고, 안 매긴 것은
"별점 없음"으로 맨 뒤에 모인다. 폴더를 눌러 그 안을 보고 `‹` 로 돌아온다 — 폴더 탭의 폴더와
같은 방식이다. 마지막 항목이 빠져 폴더가 사라지면 빈 화면에 붙들지 않고 목록으로 되돌린다.

위쪽 칸에 **작품명으로 검색**할 수 있다. 검색 중에는 폴더를 무시하고 전체에서 찾는다 —
어느 별점에 넣었는지 모르니까 찾는 것이다. 글자마다 시트를 통째로 다시 그리면 입력 칸이
포커스를 잃으므로 결과 영역만 갈아 끼운다.

되돌리기는 상태만 바꾸고 별점은 남긴다.

**감상 완료에서는 지울 수 없다.** 지우는 대신 휴지통으로 한 단계 물린다 — 영구 삭제는
휴지통에서만 할 수 있어서, 되돌릴 기회가 항상 한 번은 남는다.

두 보관함 모두 **체크박스로 여러 개를 한꺼번에** 되돌리거나 옮길 수 있다. 하나라도 고르면
위에 처리 줄이 뜨고, "전체 선택" 은 지금 보이는 것(검색 결과나 열어 둔 묶음)만 집는다.

되돌리기만 그냥 되고, **휴지통과 삭제는 한 건이든 여러 건이든 창으로 되묻는다** — 한 건이면
제목을, 여럿이면 몇 편인지를 보여 준다. 예전에는 줄 안에서 글씨를 바꿔 물었는데
(`arch.pendingDel`), 그 상태가 검색·묶음 이동 때마다 따로 지워 줘야 하는 짐이었다.
창으로 옮기면서 그 칸도 함께 없앴다.

별점은 `work.rating` (1~5, 안 매겼으면 `NULL`) 한 칸에 담긴다.

## 테마 색

기본은 **흰 바탕에 주황 포인트**(`#E8590C`)이고, **설정에서 바꿀 수 있다.** 아래 「색 고르개」와
같은 물건을 쓴다. 고른 색 하나에서 강조색 셋(`--accent` · `--accent-ink` · `--accent-soft`)과
**바탕·선·글자색까지** 만들어 낸다.

회색들도 함께 바뀐다. 강조색만 갈면 바탕과 선이 옛 색조로 남아 화면이 두 색으로 갈린다.
표면은 순백이고, 나머지는 고른 색을 아주 옅게(채도 6~16%) 머금는다. 무채색을 고르면
그 옅은 색기마저 0이 되어 진짜 회색이 된다.

명도(HSL의 L)는 눈에 보이는 밝기와 다르다 — 노랑은 파랑보다 훨씬 밝게 느껴져서, 고정 명도를
쓰면 어떤 색에서는 글자가 안 읽힌다. 그래서 **색상마다 대비를 재서** 4.5:1을 처음 넘는 명도를
찾는다. 회색·검정처럼 색이 없는 값은 채도를 끌어올리지 않는다 — 올리면 색상 0(빨강)이 튀어나온다.

라이트에서는 **고른 밝기를 되도록 지킨다** — 어두운 초록을 골랐는데 밝은 초록이 나오면
고른 것 같지가 않다. 대비가 모자랄 때만 거기서부터 어둡게 내린다. 다크에서는 고른 값이
어두우면 아예 안 보이므로 밝기를 통일한다.

색상환 24색과 극단값(노랑 · 청록 · 남색 · 회색 등 13색)을 라이트·다크 양쪽에서 실제 렌더링
값으로 재서 전부 통과함을 확인했다. 시스템 테마가 바뀌면 밝기 기준이 달라지므로 다시 만든다.

`styles.css` 의 `:root` 에도 기본 주황 팔레트를 적어 둔다. 화면이 처음 뜨는 순간 JS가 아직
돌기 전이라, 없으면 옛 색조가 한 번 번쩍인다.

### 새로 고칠 때의 번쩍임

그 기본 팔레트 때문에, 다른 색을 골라 둔 사람은 **새로 고칠 때마다 주황이 한 번 보였다가**
고른 색으로 바뀌었다. 색은 서버에서 받아 와야 알 수 있는데 그때는 이미 첫 그림이 끝난 뒤다.

`applyTheme` 이 화면에 얹은 값을 그대로 `localStorage` 에 담아 두고, `index.html` 의
`<head>` 에 있는 짧은 스크립트가 **첫 그림 전에 그것부터 되살린다.** 담아 두는 것은 계산 결과
(`--accent` · `--bg` 같은 최종 값)뿐이라 **색을 만드는 계산은 `app.js` 한 곳에만 있다** —
head 스크립트는 받아 적기만 한다. 상단바 색(`theme-color`)도 같이 담는다.

`app.js` 를 통째로 치우고 열어도 화면이 고른 색으로 나오는 것으로 확인했다.

로그아웃할 때는 담아 둔 값을 지운다 — 안 그러면 다음 사람이 로그인할 때 앞사람 색이 한 번
스친다. 새 기기에서의 첫 방문은 담아 둔 것이 없으니 여전히 한 번 번쩍인다.

## 제목의 공백

`og:title` 안에 줄바꿈과 들여쓰기를 그대로 넣어 둔 페이지가 있다. 그대로 담으면 제목 한 줄이
화면을 가로지른다. 값을 뽑는 자리에서 **이어진 공백을 한 칸으로 줄인다** — 제목뿐 아니라
설명·사이트 이름 등 OG 값 전부에 같이 적용된다. 이미 담긴 제목은 `PRAGMA user_version` 으로
한 번만 도는 이관이 편다.

## 캘린더 점 색

달력 칸과 목록에서 작품은 **색 점**으로 표시된다. 기본은 플랫폼 색이지만, 같은 플랫폼 작품이
여럿이면 서로 구분이 안 된다. 그래서 **작품마다 색을 고를 수 있다.**

## 색 고르개

작품 색·도메인 색·테마 색은 **같은 고르개 하나**를 쓴다(`colorPickerHtml` · `wireColorPicker`).
**네모 + 값 칸 + 되돌리기 버튼**이고, 네모를 누르면 **브라우저·운영체제가 주는 색 고르기 창**이
열린다. 견본 목록도, 직접 그린 사각형도 걷어냈다 — 직접 그린 것은 한 번에 한 색상의 명암만
보여줘서 색 자체를 바꾸려면 슬라이더를 따로 만져야 했다. 운영체제 창은 색상환 전체를 한 화면에
펼치고, 스포이트와 최근 쓴 색까지 딸려 온다.

값은 `#rrggbb` 로 읽고 쓸 수 있다. 네모와 값 칸 중 어느 쪽을 만져도 나머지가 따라온다.

고르기 창은 **고르는 동안 `input`, 확인을 눌러야 `change`** 를 보낸다. `change` 를 기다리면
색을 끌어도 화면이 그대로여서 "눌러도 안 바뀐다" 가 된다. 그래서 `input` 으로 받는다.
테마 색은 그 값이 화면 전체를 다시 칠하므로, 화면은 즉시 따라가되 **저장은 손이 멎고 350ms 뒤**
한 번만 한다. 저장 후에도 설정 창을 다시 그리지 않는다 — 다시 그리면 고르던 고르개가 사라진다.

"자동" 을 누르면 플랫폼 색으로 돌아간다(`work.color` 가 `NULL`). 그때 값 칸은 비고,
자리표시로 플랫폼 색이 보인다.

**담을 때부터 고를 수 있다.** URL 추가와 직접 입력에도 같은 고르개가 있다 — 다만 주기를
매주·매월처럼 날짜에 놓이는 것으로 정해야 나타난다. 미정인 채로는 달력에 안 놓이니 고를 것도 없다.

**도메인 색도 같은 고르개를 쓴다.** 다만 도메인 색은 비울 수 없어서 버튼이 "기본색" 이고,
누르면 플랫폼 기본값으로 되돌린다.

팔레트는 **달력의 어느 날에 놓이는 주기**(매주·격주·매월·날짜 지정)일 때만 보인다.
상시·완결처럼 날짜가 없는 작품에는 고를 이유가 없다.

## 회차 배지

표지 아래쪽에 회차를 붙인다. 다만 **글(블로그) 매체는 회차 개념이 없다** — 블로그 하나가
작품 하나이고, 주소의 숫자는 회차가 아니라 글 번호다. 그래서 `mediaType === "text"` 이면
회차를 저장하지 않는다. 플랫폼 이름을 열거하지 않으므로 앞으로 블로그 계열이 늘어도 그대로
적용된다 (지금은 네이버 블로그와 티스토리가 걸린다).

길이는 화면에서 묶는다. 배지는 한 줄만 쓰고 표지 폭의 70%를 넘으면 `...` 로 자른다 —
줄바꿈되면 표지를 덮고, 한 줄에 딱 맞아도 표지를 가로질러 읽기 어려워진다.

## 찾기

**전체 검색** — 상단바의 🔍. 제목으로 찾고, 보관함(감상 완료·휴지통)에 내려둔 것까지 함께
찾는다. 어느 구간에 넣었는지 몰라도 되는 게 요점이라, 결과에는 구간 이름과 상태를 붙인다.
활성 작품이 먼저 나온다.

좁은 화면에서는 **검색이 사이드 메뉴로 간다.** 상단바가 빠듯해 한때 로고를 접어야 했는데,
검색이 메뉴로 가면서 로고가 돌아왔다.

**구간 전체 목록** — 페이지 탭의 구간은 가로 슬라이드라 쌓이면 끝을 못 본다. 머리글 오른쪽 **☰** 를
누르면 그 구간의 작품이 전체 화면에 세로로 펼쳐진다. 여덟 편이 넘으면 그 안에서도 검색할 수
있다 — 적을 때는 검색칸이 자리만 차지하므로 띄우지 않는다.

## 표시 이름

친구에게 보이는 유일한 신원이라 **설정 화면에서 언제든 고칠 수 있다**(로그아웃 버튼 위).
예전에는 친구를 처음 추가할 때만 정할 수 있었다. 아직 안 정했으면 그 자리에서 알려준다 —
친구 기능을 쓰려면 필요하기 때문이다.

## 손으로 만지는 화면

**모든 시트가 같은 물건이다.** 낮은 시트든 화면을 거의 다 덮는 시트든, 맨 위에 같은 손잡이가
있고 같은 방식으로 닫힌다. 한때 큰 시트만 `✕` 버튼을 달고 손잡이가 없었는데, 창마다 닫는
방법이 다르면 매번 어디를 눌러야 하는지 찾게 된다. 끌어 내리거나, 드러난 배경을 누르거나,
`Esc` 를 누르면 닫힌다.

**닫기 버튼은 마우스가 있는 기기에만 둔다.** 끌어 내려 닫는 것은 손가락의 방식이라 마우스로는
어색하다. 가르는 기준은 화면 너비가 아니라 **포인터 종류**다
(`@media (hover: hover) and (pointer: fine)`) — 너비로 가르면 큰 태블릿에서 마우스도 없는데
버튼이 나오고, 창을 줄인 데스크톱에서는 사라진다. 마크업에는 늘 넣어 두고 보일지만 CSS가
정하므로, 창 크기가 바뀌어도 알아서 맞는다. 사이드 메뉴도 같다.

**아무리 긴 시트라도 상단바 자리는 남긴다** (`max-height: calc(100% - var(--bar-h))`).
뒤에 무엇이 있었는지 보이고, 그 자리를 눌러 닫을 수도 있다 — 전체 화면 시트에 배경이 아예
없어서 닫기 버튼이 유일한 출구이던 문제가 같이 풀린다. 높이는 글꼴이 늦게 오면 달라지므로
상단바를 실제로 재어 `--bar-h` 에 담는다.

시트는 **아래로 끌어 닫는다.** 90px 넘게 내리면 닫히고, 그보다 짧으면 제자리로
돌아온다. 손잡이뿐 아니라 **시트 어디를 잡아도** 된다 — 손잡이만 잡히던 때는 겨냥이 까다로웠다.

시트 안쪽도 스크롤되므로 두 가지가 겹치지 않게 가른다.

- **스크롤이 맨 위에 있을 때만** 시작한다. 목록을 내려 보다 창이 닫히면 곤란하다.
  맨 위인지 볼 때 **1px 여유**를 둔다 — 화면 배율이나 관성 스크롤 때문에 0.5 같은 값이
  남아 있으면 눈으로는 맨 위인데 드래그가 안 먹는다.
- 다만 **머리 영역(`.sheet-top`)을 잡았을 때는 예외**다. 손잡이·닫기 버튼·제목줄이 있는
  그 줄은 닫으라고 있는 자리라, 목록을 한참 내려 본 뒤에도 잡으면 바로 끌린다.
  한때 손잡이(4×34짜리 작은 막대)만 예외였는데 겨냥이 까다로웠다 — 화면 너비만큼 넓어졌다.
- **세로로 8px 넘게** 움직여야 드래그로 친다. 그 안에서 손을 떼면 그냥 누른 것이라 버튼이
  정상으로 눌린다. 반대로 끌고 나서 손을 뗀 자리의 버튼은 눌리지 않게 그 클릭 한 번을 막는다.
- 가로로 더 갔으면 가로 슬라이드로 본다.
- 글자를 고르거나 값을 넣는 칸에서는 아예 시작하지 않는다 — 거기선 끄는 뜻이 다르다.

맨 위에서 더 당기면 뒤 화면이 딸려 오거나 당겨서-새로고침이 떠서 드래그가 끊긴다 —
`overscroll-behavior: contain` 으로 스크롤을 시트 안에 가둔다. 전체 화면 시트에도 같이 적용되며,
거기서는 본문이 스크롤 주체다.

**사이드 메뉴는 화면 맨 끝까지 이어진다.** 시트는 아래에 붙는 물건이라 보이는 높이
(`100dvh`)에 맞춰야 하지만, 메뉴는 옆에서 나오는 판이라 주소창 자리에서 흰 바탕이 끊기면
잘려 보인다. 그래서 메뉴만 `100lvh` — 주소창이 접혔을 때의 큰 높이 — 를 쓴다.

대신 맨 아래 줄(설정 · 작품 수)은 주소창에 가리지 않게 그만큼 띄운다.
`100lvh − 100svh` 가 주소창 높이이고 **늘 같은 값**이라, 주소창이 접히든 펴지든 그 줄의
자리가 움직이지 않는다. 주소창이 없는 곳(데스크톱)에서는 0 이라 아무 일도 없다.

**사이드 메뉴도 같은 방식으로 끌어 닫는다.** 다만 축이 다르다 — 시트는 아래로, 메뉴는
**왼쪽으로**. 그래서 손잡이도 가로 막대가 아니라 **세로 막대**이고, 메뉴의 오른쪽 가장자리
한가운데에 둔다. 판단 규칙은 같다: 세로로 더 갔으면 목록을 훑는 것으로 보고, 오른쪽으로
끌면 아무 일도 일어나지 않는다.


가로 슬라이드는 **마우스로도 잡아끌 수 있다.** 손가락으로는 그냥 밀리지만, 마우스로는
휠을 옆으로 굴리거나 Shift+휠을 알아야 했다. 손가락 쪽은 브라우저가 이미 굴려 주므로
`pointerType === "mouse"` 일 때만 다룬다 — 두 벌이 겹치면 서로 싸운다. 8px 넘게 움직여야
미는 것으로 치고, 그 뒤에 오는 클릭 한 번은 삼킨다. 밀었는데 카드가 열리면 곤란하다.
끄는 동안은 스크롤 스냅을 꺼 둔다 — 켜 두면 미는 족족 도로 당긴다.

페이지 탭의 가로 슬라이드는 화면 끝까지 흘러야 자연스러워서 `margin: 0 -16px` 로 여백 밖으로
빼고 안쪽 `padding` 으로 첫 카드를 들여 놓는다. 그런데 **스크롤 스냅은 그 padding 을 모른다** —
첫 카드를 컨테이너 끝에 붙여 버려 여백이 사라진다. `scroll-padding-left` 로 스냅에도 같은
여백을 알려 준다.

카드 제목은 **한 줄이든 두 줄이든 두 줄 높이**를 차지한다(`min-height: 2.6em`). 안 그러면
제목 길이에 따라 아래 시간 줄이 카드마다 오르내린다.


**두 번 톡 쳐도 확대되지 않는다.** 누를 수 있는 요소에 `touch-action: manipulation` 을 준다.
손가락으로 벌리는 확대는 그대로 둔다 — 막으면 눈이 불편한 사람이 화면을 키울 길이 없어진다.

입력칸을 눌렀을 때 확대되던 건 다른 문제였다. **iOS 는 글자가 16px 보다 작은 입력칸에
포커스가 가면 화면을 확대한다.** 좁은 화면에서만 입력칸 글자를 16px 로 올려 막는다.

폴더 아이콘은 견본 열두 개 중에 고르거나, 그 옆 **＋** 를 눌러 직접 넣는다. 입력칸을 처음부터
보여 주면 견본과 어느 쪽을 쓰라는 건지 헷갈려서 눌러야 나오게 했다. 이미 견본에 없는 아이콘을
쓰고 있던 폴더는 열자마자 그 칸이 열려 있다.

**이모지만 받는다.** 글자나 숫자가 섞이면 마크가 아니라 이름처럼 보인다. 사람 눈에 한 글자로
보이는 단위로 잘라 첫 이모지 하나만 남기므로, `👨‍👩‍👧` 처럼 여러 부호가 이어진 것도 통째로 들어간다.


**서버를 기다리는 버튼은 그동안 눌리지 않는다.** 폴더 만들기처럼 응답이 와야 창이 닫히는
자리는, 잠깐 아무 반응이 없어 사람이 다시 누른다 — 그러면 누른 만큼 만들어졌다. `guard` 가
처리 중인 동안 뒤따라 오는 호출을 흘려보내고, 누른 버튼을 `disabled` 로 두어 눌리지 않는
것이 눈에도 보이게 한다. 여섯 번 연달아 눌러도 하나만 만들어진다.

왼쪽 아래 **＋** 는 화면 맨 아래에서 좀 띄운다. 모바일은 앱이 화면 전체를 쓰는데, 그 끝은
홈 인디케이터와 브라우저 바에 가려 버튼이 잘려 보인다. 기기가 알려주는 여백
(`env(safe-area-inset-bottom)`)에 좁은 화면에서는 26px 을 더한다. 이 규칙은 `.fab` 정의보다
**뒤에** 두어야 한다 — 미디어 쿼리는 특이성을 올려 주지 않아서, 앞에 두면 뒤의 규칙에 밀린다.

## 주간은 요일 목록이 제 통을 갖는다

좁은 화면에서는 일곱 요일이 세로로 쌓인다. 문서 전체가 굴러가던 때는 오늘이 어디쯤인지
매번 찾아야 했다 — 요일 차례가 늘 월→일 이라 오늘이 한가운데 끼어 있을 수 있기 때문이다.

이제 요일 목록만 제 통(`.week-scroll`)에서 구르고, **열 때 오늘을 맨 위로 올려 둔다.**

**높이는 재서 정한다.** 숫자로 박아 두면 글꼴·기기·주소창에 따라 매번 어긋난다.
통이 화면에서 시작하는 자리를 재서 아래까지 채운다(`fitWeek`). 넓은 화면은 일곱 요일이
나란히 서므로 굴릴 것이 없어 높이도 재지 않는다.

**끝에 빈 자리를 둔다.** 요일 차례가 고정이라 오늘이 앞쪽(월·화)이면 아래에 남은 것이
모자라 맨 위까지 못 올라간다. 모자란 만큼만 뒤에 자리를 둔다 —
`max(0, 오늘자리 + 통높이 − 안쪽길이)`. 넉넉히 두면 아무 날에나 허공이 딸려 온다.

테두리와 둥근 모서리는 **통이 갖는다.** 굴러도 제자리에 있어야 하고, 표가 벗어난 빈 자리까지
한 틀로 감싸야 하기 때문이다. 안쪽 표는 테두리를 벗는다 — 둘 다 두르면 두 겹이 된다.

**화면 끝까지 채우지는 않는다.** 남는 자리의 3분의 2쯤만 쓰고 나머지는 아래의
「공개 예정」 단락에 넘긴다. 통이 화면을 다 먹으면 그 아래에 무엇이 있는 줄도 모른다.

## 월간은 옆으로 밀어 넘긴다

화살표(`‹ ›`)는 그대로 두되, 달력을 넘기는 일은 손으로 종이를 넘기는 일에 가깝다.
달력판을 옆으로 밀면 달이 넘어간다 — **왼쪽으로 밀면 다음 달**이다.

세로로 읽는 것과 겹치지 않게 두 가지로 가른다.

1. **10px 넘게 움직였을 때, 가로가 세로보다 클 때만** 가져온다. 세로가 크면 그 손짓은
   놓아 준다 — 달력을 읽으려고 굴리는 중이다.
2. CSS 의 `touch-action: pan-y` 가 짝을 이룬다. 세로 굴리기는 브라우저에 맡기고 가로만
   우리가 받는다. 둘 다 우리가 하면 손맛이 무거워진다.

**손을 절반만 따라간다**(`dx * 0.45`). 끝까지 따라오면 다음 달이 벌써 온 것처럼 보이는데,
60px 을 못 넘기고 놓으면 제자리로 돌아오므로 거짓말이 된다. 덜 밀고 놓으면 전이가 되돌린다.

넘어가면 **넘어온 쪽에서 미끄러져 들어온다.** 화살표로 넘겨도 같다 — 둘 다 `moveMonth(n)`
한 자리로 모았다. 어느 쪽으로 갔는지가 눈에 남아야 몇 달을 넘겼는지 헷갈리지 않는다.

밀고 나서 손을 뗀 자리의 날짜가 눌린 것으로 처리되므로, **그 한 번의 클릭만 삼킨다** —
가로 슬라이드(`.rail`)와 같은 수법이다.

## 훑는 자리와 다루는 자리

목록이 나오는 곳은 모두 **두 겹**이다.

| | 모양 |
|---|---|
| 훑기 | 단락마다 **가로 슬라이드** (`.plat` · `.rail`) |
| 다루기 | **격자** — 폴더 안과 같다 (`gridHtml`) |

☰ 로 그 단락 전부를 펴고, `‹` 로 되돌아온다. **창을 새로 쌓지 않고** 같은 창 안에서
갈아 끼운다 — 창이 쌓이면 어디까지 돌아가야 하는지 알 수 없다.

이 두 겹을 쓰는 곳: 추가 목록 · 캘린더의 공개 예정 · **날짜 더보기**(매주·격주·매월 묶음마다
☰ 가 있다) · 페이지 탭의 구간 목록.

세부를 격자로 바꾼 이유는 단순하다 — 목록을 훑는 일은 결국 **표지를 보는 일**인데,
한 줄씩 늘어놓으면 표지가 너무 작다.

## 더보기는 주간·월간이 한 모양

하루에 다섯 편까지만 보이고 나머지는 `＋N편 더보기` 로 넘어간다. 주간의 요일 칸과 월간의
날짜 목록이 **같은 버튼**을 쓴다 — 마크업은 처음부터 같았는데 모양 규칙이 `.colb` 안으로
매여 있어서, 월간에서는 아무 모양도 입지 않은 맨 버튼이 나왔다. 규칙을 `.more` 로 풀었다.

## 차례는 최근 실행 순

목록의 차례는 **마지막으로 보러 간 때**다. 한때 많이 본 순이었는데, 그러면 새로 담은
작품이 늘 맨 뒤로 가서 정작 챙겨야 할 것이 안 보였다. 담을 때 `last_at` 을 지금으로
두므로 **새로 담은 것이 맨 앞에** 선다.

### 아직 안 본 것에는 붉은 점

표지 오른쪽 위에 붙는다(`visits === 0`). 새것이 맨 앞에 서므로, 그것이 "새로 온 것" 인지
"늘 거기 있던 것" 인지 가르는 표가 하나 있어야 한다.

**눌러 보면 꺼진다**(`POST /api/works/:id/seen`). 이때 `last_at` 은 건드리지 않는다 —
그건 **실제로 보러 간 때**이고 차례를 정하는 값이라, 열어만 봐도 앞으로 튀어 오르면
차례가 뜻을 잃는다. 화면에서 먼저 지우고 서버에는 조용히 알린다.

> **`.map(workCard)` 로 부르지 말 것.** `workCard(w, when)` 의 둘째 자리는 시각 자리에
> 넣을 글인데, `map` 은 거기에 **번호**를 넘긴다. 그래서 카드마다 `0 · 1 · 2 …` 가 찍혔다.
> 부르는 쪽은 `.map(w => workCard(w))` 로 적는다.

## 하루에 몇 편까지 보일까

달력은 하루에 몰린 편수만큼 칸이 길어져서, 작품이 쌓이면 끝없이 늘어났다.
**한 칸에 다섯 편까지만** 보이고 그 아래 `＋N편 더보기` 가 붙는다. 누르면 그날 전체가
전체 화면 목록으로 열리고, 거기서 작품을 고르면 위에 겹쳐 뜬다.
주간의 요일 칸과 월간의 날짜 칸이 **같은 규칙**을 쓴다 — 같은 것을 보는 두 가지 방식일 뿐이다.

### 무엇이 먼저 오는가

한 칸에 매주·격주·매월·날짜 지정이 뒤섞여 있으면 무엇이 **오늘만의 일**인지 안 보인다.
그래서 **날짜 지정이 맨 위**다 — 그날 하루뿐인 일이라 놓치면 끝이고, 매주 오는 것은
다음 주에도 온다. 다섯 칸 안에 들어오는 것도 그 차례를 따른다.

더보기 팝업에서는 아예 **주기별로 나눈다**: `날짜 지정 → 매주 → 격주 → 매월`.
날짜 지정이 먼저이고 나머지는 자주 오는 순이다. "매월 며칠" 과 "매월 몇째 주 무슨 요일" 은
셈이 다를 뿐 보는 사람에게는 한 가지라 **매월** 하나로 묶는다.

묶음은 페이지 탭과 **같은 모양**이다 — 제목 아래 가로 슬라이드, 그 안의 차례도 페이지 탭과
같은 **최근 본 순**. 같은 물건은 같게 보여야 한다.

## 배경을 눌러 닫기

`back.addEventListener("click", ...)` 한 줄이다. 시트 자체를 누른 것은 그대로 흘려보낸다.

한때 이 자리에 `touchstart` · `touchend` · `pointerdown/up` 을 손으로 엮어 두었다.
아이폰에서 배경 톡이 한 번에 안 먹는다고 **짐작하고** 덧붙인 것인데, 확인된 원인이 아니었고
손짓 사이에 상태가 남아 **시트 안 버튼이 아예 안 눌리는** 더 큰 탈을 냈다. 전부 걷어냈다.
증상을 못 잡을 때 층을 더 쌓는 것보다, 쌓은 것을 걷어내고 가장 단순한 자리로 돌아가는 편이 낫다.

## 못 읽는 곳과 안 내놓는 곳

읽어 오지 못한 이유는 둘이고, 화면에서 갈라 말한다.

| `origin` | 뜻 | 화면에 쓰는 말 |
|---|---|---|
| `og` | 받아 왔다 | 페이지가 공개한 정보에서 가져왔습니다 |
| `none` | 읽었는데 그 페이지에 없다 | …작품별 정보를 공개하지 않아 직접 입력합니다 |
| `blocked` | 아예 못 읽었다 | …자동 읽기를 막고 있어 직접 입력합니다 |

CGV가 그렇다. 페이지에는 `og:title` 도 `og:image` 도 다 걸려 있지만, Cloudflare 봇 차단이
우리 요청에 **403**을 준다 ("비정상적으로 CGV에 접속한 것이 확인되어…"). 브라우저인 척
User-Agent 를 바꾸면 뚫릴 수도 있지만, 사이트가 명시적으로 막아 둔 것을 우회하지 않는다 —
이 앱이 지켜 온 "사이트가 공개한 것만 읽는다" 와도 어긋난다.

막힌 것을 "정보를 공개하지 않는다" 고 하면 사실이 아니고, 다음에 무엇을 하면 되는지도
이어지지 않는다. 원인을 바로 말한다.

## 제 이야기를 하지 않는 페이지

읽기는 읽었는데 **작품 이야기가 아닌** 태그를 받는 경우가 있다. 카카오페이지가 그렇다 —
화면을 브라우저에서 그리는 곳이라, 어느 작품 주소로 들어가도 서버는 똑같은 대문용 태그를
내놓는다.

```
og:title   카카오페이지            ← 사이트 이름
og:url     https://page.kakao.com  ← 물어본 주소가 아니라 대문
og:image   .../shared/ogImage.png  ← 작품 표지가 아니라 공용 로고
```

그걸 그대로 담으면 **작품마다 같은 로고가 표지로** 붙는다. 그러느니 없는 편이 낫다 —
표지가 없으면 제목 첫 글자로 만든 그림이 들어가고, 그건 적어도 작품마다 다르다.

가리는 잣대는 셋이고, **어느 것도 사이트 이름을 적어 두지 않는다.**

1. 제목이 플랫폼·도메인 이름과 똑같다.
2. **이름 없이 그림만** 있다.
3. **깊은 주소를 물었는데** `og:url` 이 대문을 가리키고, **제목마저 사이트 이름**이다.

2번은 네이버 지도 같은 곳이다. 가게 페이지를 브라우저에서 그려서 서버 HTML 에는 상호가
아예 없고, `og:image` 로 지도 서비스 로고 하나만 준다.

```
og:type    website
og:image   .../maps/assets/images/og-map-400x200.png   ← 회색 지도 그림
(og:title 도 og:url 도 <title> 도 없다)
```

제 이야기를 하는 페이지는 **이름부터 밝힌다.** 이름 없이 그림만 내놓는 곳은 대개 서비스
공용 로고를 주므로, 어느 가게를 담아도 같은 회색 지도가 표지로 붙는다.

3번은 두 신호가 겹칠 때만 본다. `og:url` 하나만으로 버리면 그 태그를 대충 적어 두었을 뿐
제목과 그림은 멀쩡한 곳까지 잃는다. 대문을 물은 경우(블로그 홈처럼 제목이 곧 사이트 이름인
곳)는 깊은 주소가 아니라 애초에 걸리지 않는다.

걸리면 제목과 표지를 **함께** 버린다. 제 이름도 못 대는 페이지의 그림을 믿을 이유가 없다.

## 표지가 그리다 마는 것처럼 보일 때

표지는 남의 CDN(네이버·카카오·인스타그램·넷플릭스…)에서 그대로 가져다 쓴다. 두 가지를 했다.

**① Referer 를 보내지 않는다**(`<meta name="referrer" content="no-referrer">`).
그런 곳은 대개 다른 사이트에서 부르는 것을 막는데, 그 판단을 Referer 로 한다. 아예 안
보내면 "어디서 왔는지 모르는 요청" 이 되어 통과하는 경우가 많다. 덤으로 우리 주소를
CDN 마다 알리지 않는다.

**② 비율 재기를 한 번에 넷씩만 한다.** 한때 화면에 있는 표지를 통째로 걸어 두었다.
그러면 그림 하나가 두 번씩 불린다 — 배경으로 한 번, 재려고 또 한 번 — 그런 요청이 수십 개
한꺼번에 나간다. 브라우저는 한 서버에 여섯 줄쯤만 열어 두므로 나머지는 줄을 서고,
그동안 화면에 보여야 할 표지가 뒤로 밀려 **그리다 만 것처럼** 보였다.

재는 일은 급하지 않다 — 다음에 열 때까지 안 끝나도 그만이고, 한 번 재면 서버에 남아
두 번 재지 않는다. 그래서 한 프레임 뒤에 시작해 그리기에 자리를 내주고 천천히 뒤따른다.
하나가 막혀도(`onerror`) 줄은 계속 흐른다.

## 표지를 직접 넣기

작품 설정에 **표지** 칸이 있다. 자동 읽기가 막힌 곳이나, 받아 온 표지가 마음에 안 들 때 쓴다.
길은 둘이다.

**① 사진 고르기** — 캡처해 둔 포스터를 그대로 올린다. 아이폰 사파리에는 **"이미지 주소 복사"
가 없어서**(사진 앱에 저장 · 복사뿐이다) 주소만으로는 길이 막힌다. 이쪽이 주된 길이다.

**② 이미지 주소** — 안드로이드 크롬이나 데스크톱에서는 그림을 길게 눌러(오른쪽 클릭)
주소를 얻을 수 있다. 서버에 아무것도 남기지 않는 게 장점이다.

미리보기는 오른쪽 두 칸(사진 고르기 · 주소)과 위아래 끝을 맞춘다. 46×61 짜리로는 무엇이
담겼는지 알아보기 어려웠다.

맞추는 방향에 걸림돌이 하나 있었다. 처음에는 높이를 `align-items: stretch` 로 옆 칸에
맞추고 `aspect-ratio: 3/4` 로 너비를 얻으려 했는데, **너비가 0이 됐다** — 가로 배치에서
늘어난 높이는 너비가 정해진 **뒤에** 계산되므로 비율이 거꾸로 너비를 구해 주지 못한다.
그래서 방향을 뒤집었다: **그림이 너비(70px)와 비율로 높이를 정하고, 오른쪽 두 칸이 그 높이에
맞춰 벌어진다**(`justify-content: space-between`). 버튼이나 글꼴이 바뀌어도 끝이 어긋나지 않는다.

### 올린 그림은 화면에서 줄여 보낸다

보내기 전에 **긴 변 400px · JPEG 0.8** 로 줄인다 (`shrinkImage`). 표지를 실제로 그리는 크기가
46~120px 라 400px 이면 넉넉하고, 원본을 그대로 두면 한 장에 몇 MB가 된다.

| 담은 작품 | 차지하는 용량 |
|---|---|
| 100편 | 약 4MB |
| 1,000편 | 약 40MB |

게다가 **올린 표지가 있는 작품만** 파일을 갖는다 — 나머지는 주소를 쓰므로 0바이트다.
줄이는 일은 브라우저의 canvas 가 한다. 서버에 이미지 라이브러리를 들이지 않으려는 것이고,
덤으로 사진의 위치정보(EXIF)도 함께 떨어져 나간다.

### 관리

- 파일은 `data/covers/<작품id>.<확장자>` 하나뿐이다. 바꾸면 옛것을 지우고 덮어쓴다.
- **작품을 지우면 표지 파일도 지운다** — 안 그러면 주인 없는 파일만 쌓인다.
- 올리는 쪽에서 형식(JPEG · PNG · WebP)과 크기(1MB)를 가른다. 1MB 는 줄이기가 어긋났을 때를
  막는 빗장이지 실제로 닿는 값이 아니다.
- 몸통은 그림 바이트 그대로다 — 한 파일짜리 업로드에 multipart 를 끌어들일 이유가 없다.
- 내주는 주소 끝에 시각을 붙인다. 파일 이름이 그대로면 브라우저가 옛 그림을 계속 써서,
  바꿨는데 안 바뀌는 것처럼 보인다.
- 새 표지를 넣을 때 `cover_aspect` 는 비운다. 옛 그림의 비율을 새 그림에 물려 쓰면
  엉뚱하게 잘린다 — 비워 두면 브라우저가 받아 보고 다시 잰다.

## 새 폴더를 만들고 돌아오기

담기 화면(URL 추가 · 직접 입력)에서 `＋ 새 폴더` 를 누르면 폴더 창이 **그 시트를 덮어쓴다**
— 시트는 하나뿐이기 때문이다. 만들고 나서 안쪽만 다시 그리면 덮인 시트는 되살아나지 않는다.

한때 그래서 만들기를 눌러도 화면이 그대로였고, 사람은 눌리지 않은 줄 알고 **또 눌렀다.
누른 만큼 폴더가 생겼다.** 두 가지를 고쳤다.

- 두 화면 모두 **시트를 통째로 다시 그리는 `shell()`** 을 갖는다. 폴더를 만들고 돌아오면
  그것을 불러 되살린다.
- 치던 값(제목 · 주소)은 `draft` 에 함께 담는다. 돌아올 때 칸에서 읽으려 해도 그 칸은
  이미 없다 — 치는 동안 담아 둬야 들고 돌아올 수 있다.

**저장하는 동안에는 그 창의 저장·취소·뒤로를 모두 잠근다** (`wireHead`). 같은 일을 하는
버튼이 머리줄과 아래 버튼줄 두 자리에 있어서, 하나만 잠그면 다른 하나로 또 누를 수 있다.

## 저장이 있는 창의 머리줄

폴더 설정 · 표시 설정 · 별점 · 표시 이름 · 직접 입력 · URL 추가 · 작품 설정 — **저장이 있는
창은 모두 같은 머리줄**을 쓴다 (`headHtml` · `wireHead`). 제목과 함께 **취소·저장**이 있고,
어느 창이든 같은 자리에 같은 버튼이 있어서 매번 찾지 않아도 된다.

**모든 시트가 같은 모양이다** — 제목은 언제나 머리에 있고 내용은 본문에 있다.
머리(`.sheet-top`)와 본문(`.sheet-body`)으로 나뉜
세로 통이고, **머리는 제자리에 있고 본문만 구른다.** 손잡이 · 닫기 버튼 · 머리줄은 모두
머리 안에 있다.

한때 낮은 시트만 다른 구조였다 — 시트 자체가 구르고 머리는 `position: sticky` 로 붙여 두는
방식. 같은 물건에 두 구조가 있으니 한쪽에서만 어긋나는 일이 이어졌다: 머리 위 8px 안여백
틈으로 내용이 비치고, 닫기 버튼이 스크롤과 함께 사라지고, 머리줄의 `top` 을 손잡이 높이만큼
손으로 맞춰야 했고, 끌어 닫기가 "어느 쪽이 구르는 통인가" 를 매번 갈라 물어야 했다.
합치고 나니 그 자리가 통째로 없어졌다 — `sticky` 도, 손계산도, 분기도 쓰지 않는다.

낮은 시트는 **내용만큼만** 커야 하므로 본문은 `flex: 0 1 auto` 다. `flex: 1` 로 두면 짧은
시트가 억지로 늘어난다. 그러다 `max-height` 에 닿으면 그때부터 본문이 구른다.

한때 손잡이 줄과 머리줄을 **따로** 붙여 두고, 머리줄의 `top` 을 손잡이 높이(24px)만큼
내려 맞췄다. 그건 손잡이 높이가 바뀌면 그대로 어긋나는 숫자였고, 바탕색과 테두리도 두 곳에
나눠 줘야 했다. 하나로 묶으니 그런 자리가 없어졌다 — 바탕색도 아래 선도 한 번만 준다.

닫기 버튼도 이 통 안에 있다. 밖에 두고 시트를 기준으로 놓았더니 두 가지가 어긋났었다 —
붙어 있는 머리줄과 쌓임 차례가 같아 아랫부분이 가려졌고(먼저 온 쪽이 아래로 그려진다),
시트가 구르는 통이라 스크롤과 함께 사라졌다.

`.sheet` 에는 **위쪽 안여백을 두지 않는다.** 두면 붙어 있는 머리 영역이 그만큼 내려앉고,
그 틈으로 내용이 비쳐 지나간다. 위쪽 여백은 머리 영역이 제 것으로 갖는다.

머리줄은 각 화면이 제 본문 첫머리에 그리므로, `openSheet` 이 그린 **뒤에** 이 통으로 옮긴다.
부르는 쪽 모양을 바꾸지 않으면서 한 통으로 묶는 가장 짧은 길이다. 전체 화면 시트의 본문 안에
있는 머리줄(날짜 미지정의 묶음 제목 같은 것)은 본문이 제 통을 갖고 구르므로 그대로 둔다 —
직계 자식만 집는다.

머리줄은 스크롤해도 붙어 있으므로 시트가 길어지면 저장 버튼이
저 아래에 있어서 한참 내려가야 했다. 붙여 두면 그 문제가 없고, 덤으로 **손잡이 대신 머리줄을
잡아 끌어도** 창을 닫을 수 있어서 겨냥할 자리가 넓어진다.

버튼이 놓이는 자리는 [닫기 버튼](#모든-시트가-같은-물건이다)과 **같은 잣대**로 가른다.

| | 자리 |
|---|---|
| 마우스가 있는 기기 | 시트 맨 아래 버튼줄 |
| 손가락 기기 | 머리줄 오른쪽 끝 |

**둘 중 하나만 보인다.** URL 추가와 직접 입력의 `목록에 등록` 은 한동안 이 규칙에서
빠져 있어서, 손가락 기기에서 머리줄의 `담기` 와 아래의 `목록에 등록` 이 한 화면에 둘씩
보였다. `actionRow(id, label)` 로 묶어 `.wide-only` 를 씌웠다.

숨겨도 **지우지는 않는다.** 이 두 화면의 실행 버튼은 미리보기를 그릴 때 함께 생기므로,
머리줄의 저장은 그 버튼을 찾아 눌러 주는 방식이다(`wireHead`). 지워 버리면 손가락으로는
담을 수 없게 된다 — `display: none` 인 버튼도 `.click()` 은 그대로 먹는다.

"삭제" 나 "기본값으로" 처럼 저장과 성격이 다른 것은 따로 둔다 — 취소·저장 옆에 두면
잘못 누르기 쉽다.

## 문서를 고정하면 sticky 가 풀린다

시트를 열면 뒷장이 구르지 않게 문서를 제자리에 고정한다(`position: fixed; top: -Ypx`).
그런데 그러면 **붙어 있던 것이 붙을 곳을 잃는다** — 상단바가 `sticky` 라, 문서가 구르지
않게 되는 순간 제 문서 자리(스크롤한 만큼 위)로 돌아가 화면 밖으로 나갔다.

그래서 시트 위에 남겨 둔 자리에 **상단바 대신 페이지 내용이 비쳤다** — 반쯤 잘린 글자가
떠 있어 무언가 새어 나온 것처럼 보였다. 고정하는 동안만 상단바를 화면에 직접 붙여 둔다
(`html.locked .app-bar { position: fixed }`). 닫으면 다시 `sticky` 로 돌아간다.

## 시트가 좌우로 흔들리던 것

`.sheet` 에 `overflow-y: auto` 만 주었더니 `overflow-x` 도 `auto` 가 되어, 안쪽 것이 조금만
넘쳐도 시트가 좌우로 흔들렸다. 가로로 흐를 것(가로 슬라이드)은 저마다 제 통을 갖고 있으므로
시트 자체는 `overflow-x: hidden` 이면 된다. 전체 화면 시트의 본문도 같다.

## 작품 설정의 저장

**주소는 저장할 때 함께 적용된다.** 주소 없이 담은 항목(직접 입력)에 나중에 주소를 붙이면
제목·표지·플랫폼을 그 페이지에서 다시 얻어야 한다. 고쳐 담을 수는 없어서 새로 담고 옛 항목을
지우되, **제목·일정·폴더·색은 그대로 옮긴다** — 사용자가 이미 정해 둔 것이다.

한때 이 일을 `붙이기` 라는 따로 된 버튼이 맡았다. 그래서 주소를 넣고 **저장만 누른 사람에게는
아무 일도 일어나지 않았다** — 표지가 안 바뀐다는 말이 그것이었다. 넣었으면 적용되는 것이
당연한 기대라, 버튼을 없애고 저장이 맡게 했다.

버튼은 **취소와 저장** 둘이고, 놓이는 자리는 기기에 따라 다르다.

| | 자리 |
|---|---|
| 마우스가 있는 기기 | 시트 맨 아래 버튼줄 |
| 손가락 기기 | `작품 설정` 제목줄 오른쪽 끝 |

두 자리를 **같은 잣대**(`(hover: hover) and (pointer: fine)`)로 가른다. 하나가 보이면 다른
하나는 숨는다 — 잣대가 다르면 어느 기기에서 둘 다 보이거나 하나도 없는 자리가 생긴다.
좁은 화면에서는 시트가 길어 맨 아래까지 내려가야 저장할 수 있었는데, 제목줄은 늘 손이 닿는다.

`‹` 로 되돌아갈 때는 담는 중이면 취소, 고치는 중이면 저장이다 — 하던 일을 잃지 않게.

## 커서를 언제 넣는가

시트가 열리면 곧바로 입력칸에 커서를 넣어 두었다. 바로 칠 수 있어 편하지만,
**아이폰에서는 이것이 여러 탈의 뿌리였다.**

커서가 가면 키보드가 올라오고, 사파리는 그 칸을 보여 주려고 화면 전체를 밀어 올린다.
그러고 나면 화면에 붙여 둔 것들(덮개 · ＋ 버튼)이 **그려진 자리와 눌리는 자리가 어긋난다** —
＋ 버튼을 눌렀는데 뒤에 있는 목록이 눌리는 식이다. 창을 닫아도 어긋남이 남았고,
뒷장 스크롤을 막아 두어도 이 상태에서는 이상하게 굴었다.

그래서 **좁은 화면에서는 커서를 넣지 않는다**(`softFocus`). 사용자가 칸을 눌러 시작한다.
넓은 화면에서는 그대로 넣는다 — 키보드가 없어 탈이 날 일이 없고, 바로 칠 수 있는 편이 낫다.

## 시트를 겹쳐 열기

날짜 미지정 목록에서 작품을 고르면 목록이 닫히고 작품 화면이 떴다. 닫으면 보던 자리가
아니라 달력으로 돌아와서, 여러 편을 훑어보려면 매번 다시 들어가야 했다.

이제 작품 화면이 **목록 위에 겹쳐** 뜨고, 닫으면 보던 목록으로 돌아온다. 날짜 미지정 ·
하루치 전체 · 폴더 · 구간 목록 · **검색**이 모두 그렇다. 검색은 치던 말과 결과까지 되살린다 —
한 편 보고 돌아왔는데 검색어가 비어 있으면 다시 쳐야 한다. 화면을 통째로 담아 두면 붙여 둔 동작들이 죽으므로, 담는 것은 **다시 여는 함수**다
(`openSheet(html, { over })`). `over` 없이 연 시트는 새 흐름이라 쌓인 것을 비운다 —
그래서 어디서 열든 닫기를 거듭하면 반드시 바닥까지 닫힌다.

## 무엇이 구르는가

넓은 화면에서는 앱이 **화면 높이에 맞춘 카드**이고 안쪽 `.screen` 만 구른다. 좁은 화면에서는
**문서 자체가 구른다** — 사파리가 주소창을 접는 조건이 그것이기 때문이다.

아이폰 사파리는 문서가 아래로 구를 때 주소창을 접어 화면을 넓혀 준다. 앱을 `100dvh` 에 못 박고
안쪽만 굴리면 문서는 한 번도 움직이지 않아, 주소창이 끝까지 펼쳐진 채 남고 그만큼 화면이 좁다.
그래서 좁은 화면에서는 앱의 높이를 풀고(`height: auto; min-height: 100dvh`) `.screen` 의
스크롤을 끈다.

그 대가로 손봐야 하는 것들이 있다.

- **상단바**는 `position: sticky` 로 붙여 둔다. 탭은 어디까지 내려가도 닿을 수 있어야 한다.
  붙는 요소는 제 배경이 있어야 해서 `--surface` 를 직접 준다. **쌓임 차례를 조심해야 한다** —
  `z-index: 7` 로 두었더니 덮개(시트 5 · 사이드 메뉴 6) 위에 그려져서, 시트를 열면 제목줄이
  상단바 뒤에 가려 통째로 잘려 보였다. 화면이 밀린 것처럼 보이지만 실은 **덮인 것**이다.
  내용 위, 덮개 아래인 `3` 이 제자리다.
- **＋ 버튼과 덮개**(시트 · 사이드 메뉴)는 `position: fixed` 로 바꾼다. `.app` 안에 매어 두면
  문서 끝까지 늘어나 버린다. 다만 `inset: 0` 으로 두면 안 된다 — 아이폰에서 `bottom: 0` 은
  **주소창이 접혔을 때의** 큰 높이에 맞춰져서, 시트가 그만큼 아래로 밀리고 위쪽(제목줄)이
  화면 밖으로 나간다. `height: 100dvh` 를 쓴다. 지금 보이는 높이를 브라우저가 직접 알려 주는
  단위라 주소창을 따라가고, **키보드에는 반응하지 않아** 입력칸에 커서가 가도 시트가 흔들리지
  않는다. (한때 `visualViewport.height` 를 재어 넣었는데, 그건 키보드에도 반응해서 오히려
  화면이 어긋났다.)
- **덮개가 떠 있는 동안은 뒷장이 구르지 않게 잠근다** — 문서를 있던 자리에 붙들어 두고
  (`position: fixed; top: -Ypx`) 닫을 때 되돌린다. `overflow: hidden` 만으로는 아이폰이
  말을 듣지 않는다. 문서가 못 구르면 그만이므로 손짓을 가로채는 장치는 두지 않는다 —
  한때 `touchmove` 를 받아 직접 막았는데, 없어도 되는 것이었고 손짓 사이에 상태가 남아
  탈만 냈다. 시트와 사이드 메뉴가 겹칠 수 있어 잠금은 세어 둔다.

- **다시 그릴 때 맨 위로 올린다.** 안쪽이 구를 때는 내용을 갈아 끼우면 저절로 맨 위가 됐는데,
  문서가 구를 때는 그렇지 않다.
- **＋ 버튼이 비켜나는 판단**은 어느 쪽이 구르든 같은 값을 읽게 한 곳(`scrolledY`)에 묶었다.
  아이폰은 문서 끝에서 더 당기면 화면을 고무줄처럼 튕기는데, **되돌아오는 움직임이
  "위로 올렸다"로 읽혀** 숨겨 둔 버튼이 다시 튀어나왔다. **튕김 자체는 그대로 둔다** —
  손맛이고 아이폰다운 움직임이라 없앨 이유가 없다. 대신 **범위(`0 ~ 최대`) 밖의 스크롤 값은
  셈에서 뺀다.** 튕기는 동안의 값은 사람이 민 것이 아니므로 버튼은 숨은 채로 있는다.

이 규칙들은 앞의 정의를 덮어야 하므로 `styles.css` 맨 끝에 모아 두었다 — 미디어 쿼리는
특이성을 올려 주지 않아서, 앞에 두면 뒤의 규칙에 밀린다.

## 폴더

폴더 탭의 각 줄 오른쪽에는 **⋮** 가 있고, 누르면 바로 폴더 설정이 열린다. 줄 본체를 누르면
폴더 안으로 들어간다. `전체` 와 `미분류` 는 진짜 폴더가 아니라 설정할 것이 없으므로 화살표만 둔다.

**폴더 안은 팝업으로 연다.** 예전에는 화면을 갈아 끼우고 `‹` 로 되돌아왔는데, 여러 폴더를
훑어보려면 매번 목록으로 나갔다 들어와야 했다. 이제 목록은 그대로 두고 그 위에 전체 화면
팝업이 뜬다. 안에서 작품을 고르면 폴더 위에 한 번 더 겹치고, 닫으면 보던 폴더로 돌아온다.

주소에는 그대로 `#lib/<id>` 로 남는다 — 새로 고쳐도 열려 있던 폴더가 다시 열린다.
그래서 `openFolderId` 는 "지금 열려 있는 폴더" 라는 뜻이 되고, 팝업을 닫을 때 같이 비운다.
끌어 내려 닫아도 마찬가지다.

제목줄 오른쪽의 `⋯` 로 그 폴더를 고칠 수 있다. 고치고 나면 보던 폴더로 돌아오고, 지우면
팝업이 닫힌다. 새 폴더를 만들면 만들자마자 열어 준다. `전체` 와 `미분류` 는 진짜 폴더가 아니라
`⋯` 가 없다.

**폴더를 지워도 작품은 남는다.** `work_folder` 에 `ON DELETE CASCADE` 가 걸려 있어 그 폴더에
대한 지정만 풀린다 — 그 폴더 하나뿐이던 작품은 미분류로 가고, 여러 폴더에 있던 작품은
나머지 폴더에 그대로 남는다.

### 여러 개 골라 한 번에 지우기

목록 위 머리줄의 **선택**을 누르면 고르는 중이 된다(`folderSel` — `null` 이면 평소 화면,
`Set` 이면 고르는 중). 폴더마다 네모칸이 생기고, **네모칸이든 줄이든 누르면 고르는 뜻이다** —
고르는 중에 폴더를 열 일은 없으므로 줄 전체를 판으로 쓴다.

고르는 동안에는 `전체` · `미분류` · `＋ 새 폴더` 와 줄 오른쪽의 `⋮` 를 감춘다. 지울 수
있는 것만 남겨 두면 "이건 왜 체크가 안 되지" 를 묻지 않아도 된다.

머리줄은 그때 **보관함의 처리 줄과 같은 모양**(`.bulk`)으로 바뀐다 — 고른 수 · 전체 선택 ·
삭제 · 완료. 같은 일을 두 곳에서 다르게 보이게 할 이유가 없어 클래스까지 같이 쓴다.

삭제는 창으로 되묻고(위 「되돌릴 수 없는 일은 한 번 더 묻는다」), 이름을 셋까지 보여 준 뒤
나머지는 "외 N개" 로 줄인다. 지운 뒤에는 고르기가 저절로 꺼진다.

## 폴더 창의 버튼

폴더를 열면 머리줄에 셋이 선다. **자리가 곧 뜻이다.**

```
🤝 같이 볼 것  👥                                    ＋  ⚙
   4개                                            넣기  설정
   └ 제목에 딸린 것 (누가 있나)          이 폴더에 하는 일 →
```

**👥 공유자**는 제목 글줄 **안에** 있다. 그건 이 폴더가 어떤 폴더인지에 딸린 값이지
이 폴더에 하는 일이 아니다. 한때 오른쪽 버튼 무리에 섞여 있었는데, 「이 폴더를 어떻게
할까」 사이에 「누가 있나」가 끼어 무엇을 하는 자리인지 흐렸다.

오른쪽은 **넣기가 먼저, 고치기가 뒤**다 — 자주 하는 쪽이 앞이다.

한때 안내말에 "오른쪽 위 ⋯ 로 폴더를 고칠 수 있습니다" 를 적어 두었다. 그건 **아이콘이
알아볼 만하지 않다는 뜻**이었다. ⋯ 를 톱니로 바꾸니 그 줄이 필요 없어졌다 — 버튼이
무엇을 하는지는 버튼이 말해야 한다.

| 폴더 | 👥 | ＋ | ⚙ |
|---|---|---|---|
| 내 보통 폴더 | | ○ | ○ |
| 내가 연 공유 폴더 | ○ | ○ | ○ |
| 불려 간 공유 폴더 | ○ | ○ | ○ |
| 그냥 비추는 폴더 | | | ○ |

비추기만 하는 폴더에 ＋ 를 두지 않는 이유는 **누를 수 있는데 아무 일도 안 일어나기**
때문이다 — 그건 남의 폴더를 보여 주는 껍데기라 걸 자리가 없다(`mayFile`).

### 폴더 쪽에서 작품을 부른다

＋ 는 이 폴더에 **아직 없는** 내 작품을 구간(도메인)별로 늘어놓고, 여럿을 골라 한꺼번에
넣는다. 반대 방향 — 작품 쪽에서 폴더를 고르는 길 — 은 작품 설정의 「폴더 바꾸기」가 이미
맡고 있는데, 그 길로 한 폴더를 스무 편으로 채우려면 작품마다 창을 열었다 닫아야 한다.

묶는 단위가 구간인 것은 **사람이 그 단위로 떠올리기** 때문이다 — "네이버웹툰 것들을
넣자" 이지 "제목이 ㄱ 인 것들" 이 아니다. 그래서 구간 머리마다 「구간 선택」이 있다.

**빼지는 않는다.** 빼는 것은 작품 쪽 일이라, 여기에 두면 같은 일을 하는 자리가 둘이 되고
"고르개에서 체크를 풀면 빠지나" 를 사람이 헷갈린다. 여기 서는 것은 넣을 수 있는 것들뿐이고,
고른 것은 더해지기만 한다.

한 번에 보내는 이유도 같은 결이다 — 한 편씩 PATCH 로 보내면 스무 편에 스무 번을 왕복하고,
중간에 하나가 어긋나면 절반만 들어간 채로 남는다.

```
POST /api/folders/:id/works   { works: [...] }  →  { added: n }
```

**넣을 곳은 원본 폴더다.** 함께 쓰는 폴더에 불려 간 쪽에서 넣으면 내 껍데기가 아니라
주인의 폴더에 걸려야 주인에게도, 함께 쓰는 다른 사람에게도 보인다.

```js
const into = mine.mirror ? mine.mirror.folder : id;
```

답으로 **실제로 들어간 수**를 돌려준다. 고른 수와 다르면 그대로 말한다 — 권한이 중간에
바뀌어 일부만 들어가는 일이 있는데, "넣었습니다" 만 말하면 없는 편을 찾으러 다니게 된다.

## 화면 상태와 주소

보던 화면은 **주소 해시**에 남는다. 새로고침해도 그 자리에 있고, 주소만 봐도 어디인지 안다.

| 해시 | 화면 |
|---|---|
| (없음) · `#cal/week` · `#cal/month` | 캘린더 (주간 · 월간) — 들어오면 여기부터 |
| `#home` | 페이지 |
| `#lib` | 폴더 목록 |
| `#lib/<폴더id>` · `#lib/_all` · `#lib/_none` | 폴더 안 |

화면 이름은 **캘린더 · 페이지 · 폴더** 이지만 주소의 열쇠(`cal`·`home`·`lib`)는 그대로 두었다 —
이미 저장해 둔 주소가 이름을 바꿨다고 깨지면 안 된다.

서버에 저장할 성질이 아니라 해시를 쓴다. 검색 문자열(`?url=`, `?invite=`)은 공유·초대가
이미 쓰고 있어 건드리지 않는다. 지워진 폴더나 알 수 없는 값을 가리키면 조용히 상위 화면으로
되돌린다 — 주소는 사용자가 손으로 고칠 수 있으므로 항상 틀린 값이 올 수 있다고 본다.

`history.replaceState` 로 적으므로 뒤로 가기 기록은 쌓이지 않는다.

## 로그인

카카오 · 네이버 · 구글 소셜 로그인을 지원한다. 셋 다 OAuth 2.0 authorization code 흐름이라
골격이 같고, `src/auth.ts` 의 `PROVIDERS` 표에 주소와 프로필 응답 모양만 적어두었다.

프로젝트 루트에 **`.env`** 파일을 만들어 값을 넣으면 `npm start` 가 알아서 읽는다
(`.env.example` 을 복사해서 채우면 된다). `.env` 는 `.gitignore` 에 들어 있다.

**자격 증명이 하나도 없으면 로그인 없이 "이 기기" 로컬 계정으로 동작한다.** 하나라도 채우면
로그인 화면이 뜨고 모든 API가 인증을 요구한다. 각 개발자 콘솔에서 앱을 등록하고
리다이렉트 URI를 `<BASE_URL>/auth/<provider>/callback` 으로 넣으면 된다 — `.env.example` 참고.

| | 필요한 값 | 등록할 곳 |
| --- | --- | --- |
| 카카오 | REST API 키 | developers.kakao.com |
| 네이버 | Client ID · Secret | developers.naver.com |
| 구글 | Client ID · Secret | console.cloud.google.com |

**기본은 최소 권한이다** — 로그인에 필요한 건 제공자가 주는 고유 ID 하나뿐이므로,
닉네임·프로필 사진·이메일을 요청하지 않는다(구글은 규격상 `openid` 하나). 받지 않으니
저장할 것도 없다. 계정 화면에 이름·사진을 띄우고 싶으면 `KAKAO_SCOPE` 처럼
`<PROVIDER>_SCOPE` 환경 변수로 켤 수 있고, 빈 값으로 두면 아무것도 요청하지 않는다.

세션은 30일짜리 HttpOnly 쿠키다. **토큰 원문은 저장하지 않고 SHA-256 해시만 남긴다** —
DB가 유출돼도 그것으로 쿠키를 만들어낼 수 없다. 로그인 왕복 사이의 `state` 는 서버가
기억했다가 대조해 CSRF를 막는다.

기본 설정에서는 개인정보를 거의 보관하지 않는다 — 제공자 이름과 고유 ID뿐이다.
`_SCOPE` 로 프로필을 켜면 그때부터 이메일·닉네임·사진을 보관하게 되므로, 공개 서비스로
운영한다면 개인정보 처리방침과 관련 법적 검토가 별도로 필요하다.

## 초대 링크는 로그인 너머로 살아남는다

초대 링크는 `/?invite=코드` 다. 그런데 링크를 받은 사람은 **아직 계정이 없는 경우가 많다** —
링크를 받고 그 자리에서 가입한다.

한때 그 길이 끊겨 있었다. 로그인 전이면 상태를 못 받아 곧장 로그인 화면으로 빠지느라 초대
코드를 읽지도 못했고, 가입을 마치면 `location.replace("/")` 로 주소가 바뀌어 코드가 사라졌다.
카카오로 들어와도 콜백이 `/` 로 보내므로 마찬가지였다. 그래서 **링크로 들어와 가입하면
친구가 맺어지지 않았다.**

로그인 화면으로 빠지기 **전에** 코드를 `sessionStorage` 에 적어 둔다. 그 탭에만 있고,
카카오에 다녀와도 남는다. 들어온 뒤에 꺼내 쓰고 지운다.

받는 쪽에 표시 이름이 없으면 이름부터 묻고, 정하고 나면 다시 친구 요청 창으로 돌아온다.

## 아이디 · 비밀번호 로그인

카카오 같은 제공자를 거치지 않는 길. `provider = "password"`, `provider_uid = 아이디` 다.

**비밀번호는 그대로 담지 않는다.** `node:crypto` 의 **scrypt** 로 요약해서 담고, 소금(salt)은
계정마다 새로 뽑는다 — 같은 비밀번호를 쓴 두 사람의 요약이 같아지지 않는다. scrypt 는 일부러
느리고 메모리를 많이 쓰는 셈법이다. 빠른 셈법(SHA 같은 것)으로 요약하면 파일을 훔쳐간 사람이
초당 수십억 번씩 맞춰볼 수 있다. 견줄 때는 `timingSafeEqual` 을 쓴다 — 몇 글자까지 맞았는지가
걸린 시간으로 새어 나가지 않게.

```
scrypt:<소금(base64url)>:<요약(base64url)>
```

**맞춰보기를 막는다.** 아이디마다 세어 두고 10분에 8번 틀리면 잠시 쉬게 한다. 비밀번호가
아무리 좋아도 무한정 두드릴 수 있으면 언젠가는 뚫린다. 서버가 살아 있는 동안만 기억한다 —
껐다 켜면 풀리지만, 몰아치는 시도를 막는 것이 목적이라 그걸로 충분하다.

**로그인 실패는 한 가지 말로만 답한다** — "아이디나 비밀번호가 맞지 않습니다".
"없는 아이디입니다" 와 "비밀번호가 틀립니다" 를 가려 말하면 어떤 아이디가 있는지 알아낼 수 있다.

받는 값은 아이디 `영문·숫자·밑줄 3~20자`, 비밀번호 `8자 이상`.

**되찾을 길은 없다.** 메일 인증을 두지 않았으므로 비밀번호를 잊으면 그 계정에는 다시 못
들어간다. 가입 화면에서 그렇게 알린다 — 있지도 않은 "비밀번호 찾기" 를 흉내내는 것보다 낫다.

게스트로 쓰던 중에 가입하면 **쓰던 계정을 그대로 데려간다** (`linkGuestPassword`) —
카카오로 로그인할 때와 같다.

## 둘러보기 (게스트)

로그인 없이 바로 쓸 수 있다. `POST /auth/guest` 가 `provider = "guest"` 인 계정을 만들고
세션 쿠키를 준다. 그 뒤로는 보통 계정과 똑같이 담고 정리한다.

**친구 기능만 열지 않는다.** 게스트는 기기에 남는 쿠키가 유일한 열쇠라, 쿠키가 지워지거나
기기를 바꾸면 그 자료에 다시 닿을 길이 없다. 되찾을 수 없는 계정으로 남과 이어지면
기기를 잃었을 때 **상대 쪽에만 흔적이 남는다.**

막는 자리는 화면이 아니라 **서버**다 — `/api/friends*` 와 `/api/invites*` 는 게스트에게
403을 준다. 폴더의 공개 설정도 저장 단계에서 무시한다. 화면에서도 가리지만, 화면은
꾸미는 것이고 실제로 막는 것은 서버여야 한다.

가리는 방식은 "버튼을 지우기" 가 아니라 **이유를 보여 주기** 다. 친구 자리를 누르면
왜 막혔는지와 로그인 버튼이 함께 뜬다. 그냥 없애면 "왜 없지" 가 되고, 눌러도 아무 일이
없으면 고장으로 보인다.

### 나중에 로그인하면

**쓰던 계정에 그대로 이어 붙인다** (`linkGuest`). 새 계정을 만들어 버리면 담아 둔 것이
게스트 계정에 갇힌 채 빈 화면으로 시작하게 된다 — 둘러보기를 권해 놓고 그렇게 되면 안 된다.
사용자 행 하나의 `provider`·`provider_uid` 만 바꾸므로 작품·폴더·설정이 전부 그대로다.

이을 수 없는 경우가 하나 있다 — **그 제공자로 만든 계정이 이미 따로 있을 때.** 그때는
잇지 않고 원래 있던 계정으로 들어간다. 두 계정을 합치는 일은 어느 쪽을 남길지 사람만
정할 수 있어서, 말없이 처리하지 않는다.

## 친구와 공유

**아이디를 검색해 아무나 추가하는 방식이 아니다.** 초대 링크를 받은 사람만 친구가 될 수 있다.
로그인 제공자에게서 프로필을 받지 않으므로, 친구에게 보이는 이름은 앱 안에서 직접 정한다 —
본명이 노출되지 않고 제공자 권한도 필요 없다.

공유는 **폴더 단위**다. 담아둔 것 전부가 아니라 "친구에게 공개"로 표시한 폴더만 보인다.
공개하지 않은 폴더, 보관함, 접속 기록은 친구에게도 보이지 않는다.

| | |
| --- | --- |
| 표시 이름 | 앱 안에서 직접 정함 (`user.display_name`) |
| 친구 맺기 | 초대 링크 → 수락. 14일 유효, 양방향으로 저장 |
| 공유 범위 | `folder.shared = 1` 인 폴더와 그 안의 활성 작품만 |
| 친구 끊기 | 양쪽 모두에서 즉시 끊긴다 |
| 즐겨찾기 | `friend.starred` — 내 줄에만 남아 상대는 모른다 |

## 친구가 많아지면

친구 목록은 세 화면에서 쓴다 — 사이드 메뉴의 **친구**, 폴더 탭의 **친구 폴더 보기**,
폴더 설정의 **고른 친구에게만**. 200명쯤 되면 훑어서는 못 찾는다.

### 첫 화면에 싣지 않는다

`/api/state` 는 **친구 수만** 내려주고(`friendCount`), 목록은 위 세 화면을 열 때
`GET /api/friends` 로 부른다. 앱을 열 때마다 딸려 오면 캘린더만 보고 나가는 사람에게는
그냥 버려지는 짐이다 — 202명이면 17KB다. 한 번 부르면 다음 `reload()` 까지 들고 있고,
`reload()` 는 목록을 비워 다음에 열 때 새로 부르게 한다(친구가 늘었을 수 있으므로).

사이드 메뉴의 `친구 N명` 은 목록이 아니라 그 숫자 하나로 그린다. 메뉴를 열었다고
목록을 부를 이유는 없다.

### 찾기와 즐겨찾기 — 끊어 불러오기는 쓰지 않는다

유튜브 댓글처럼 **스크롤이 끝에 닿으면 더 부르는 방식은 쓰지 않는다.** 댓글은 끝이 없지만
친구는 사람 수만큼이고, 무엇보다 **찾기와 정면으로 부딪힌다** — 200명 중 20명만 실려 있으면
이름을 쳐도 그 20명 안에서만 찾는다. 유튜브 댓글에 찾기가 없는 건 우연이 아니다. 댓글은
흘려 읽는 강이지만 친구 목록은 한 사람을 짚는 명부라, 필요한 것은 무한 스크롤이 아니라
**찾기와 순서**다.

그래서 두 갈래를 둔다.

- **이름을 알면 찾기** — 여섯 명이 넘으면 목록 위에 찾기 칸이 뜬다. 글자마다 목록만
  갈아 끼워 치던 자리를 지킨다.
- **자주 보는 사람이면 즐겨찾기** — 아래.

### 초대 링크는 맨 위에

이 화면에서 새로 하는 일은 초대 하나뿐인데, 버튼이 목록 아래에 있으면 친구가 쌓일수록
손이 멀어진다. 맨 위로 올렸다.

### ㄱㄴㄷ 띠

친구가 수십 명이 되면 굴려서 찾기 어렵다. 목록을 **첫소리 차례**로 묶고, 오른쪽 가장자리에
띠를 둔다. 짚으면 그 칸으로 뛰고, **짚은 채로 끌면** 지나가는 칸을 따라 목록이 움직인다.
누르는 것과 끄는 것을 가르지 않는다 — 짚은 자리가 곧 가려는 곳이다.

- **쌍자음은 홑자음 칸에 함께 넣는다.** ㄲ 만 있는 목록에서 ㄱ 을 눌렀는데 아무 데도 안
  가면 고장으로 보인다. 사람이 찾을 때 떠올리는 것은 ㄱ 이다.
- **빈 칸도 자리를 지킨다**(흐리게). 띠가 짧아졌다 길어졌다 하면 같은 자리를 짚어도 매번
  다른 데로 간다.
- 찾는 중이거나 즐겨찾기만 볼 때는 묶지 않는다 — 몇 줄뿐이라 머리글이 짐이 된다.
- 목록이 첫소리 차례가 되면서 **별 켠 사람을 위로 올리던 것은 여기서 놓았다.** 차례가 띠와
  같아야 짚은 자리로 갈 수 있다. 자주 보는 사람만 보려면 ★ 단추가 있다.

세 가지가 걸렸고 셋 다 같은 뿌리였다 — **자리를 잘못 재는 것**.

1. **붙어 있는 머리글로 자리를 재면 안 된다.** `.cho-h` 는 sticky 라, 이미 지나온 칸은
   모두 통 꼭대기에 겹쳐 서 있다. 그때 `getBoundingClientRect()` 로 재면 어느 칸을 짚어도
   같은 값이 나온다. **머리글 다음 줄**로 잰다 — 줄은 붙어 있지 않아 제자리를 알려 준다.
2. **띠가 목록과 함께 굴러 사라졌다.** 목록 안에 절대 위치로 넣었기 때문이다. `sticky` 로
   바꾸고 목록과 나란히(flex) 놓으니 굴러도 제자리에 남는다.
3. **마지막 칸이 맨 위까지 못 올라갔다.** 주간 달력과 같은 수법으로 뒤에 모자란 만큼
   빈 자리를 둔다. 그 자리를 잴 때 `:last-of-type` 을 썼다가 한참 헤맸는데, 그건
   **태그로 세는** 선택자다 — 머리글도 줄도 `div` 라 마지막 `div` 는 늘 줄이었고
   아무것도 안 잡혔다. 클래스로 골라 마지막을 집는다.

### 즐겨찾기

친구 목록에서 줄 오른쪽의 **★** 를 눌러 켜고 끈다. 켜면 목록 맨 위로 올라오고, 위쪽의
**★ 즐겨찾기** 를 누르면 켠 사람만 남는다.

`friend.starred` 한 칸이다. 친구 관계는 양쪽에 한 줄씩 담기므로 **내 줄에만** 켜면
상대는 모르는 나만의 표시가 된다 — 서로 동의할 일이 아니라서 그래야 맞다.

**켜고 끄는 곳은 친구 목록 하나뿐이다.** 폴더 바꾸기와 폴더 공개 설정에서는 별이
**켜져 있음을 보여 주기만** 하고 순서만 따라간다. 같은 스위치가 세 군데 있으면 어디서
켠 것인지 헷갈린다.

별을 눌러도 **그 자리에서 줄이 뛰지 않는다.** 서버에 보내기 전에 별부터 칠하고, 순서는
속으로만 고쳐 둔다 — 누르자마자 줄이 맨 위로 솟으면 그다음에 누르려던 사람이 어디로
갔는지 알 수 없다. 새 순서는 다시 그릴 때(찾기 · 즐겨찾기 켜기 · 다시 열기) 나타난다.
서버가 거절하면 별을 원래대로 되돌리고 알린다.

## 미러링

**작품을 베끼지 않는다.** 내 표에 생기는 것은 폴더 한 줄뿐이고(`folder.mirror_owner` ·
`mirror_folder`), 화면을 그릴 때마다 주인 것을 그대로 가져다 그 폴더 안에 놓아 준다
(`withMirrors`). 그래서 주인이 넣거나 빼거나 제목을 고치면 **다음에 열 때 바로 보인다.**

비쳐 온 작품에는 표를 달아 둔다(`work.mirror` = 주인 아이디). 이 표 하나로 갈리는 것들:

- **작품 창** — 눌러도 설정으로 안 간다. 친구 폴더를 훑을 때와 **같은 읽기 전용 창**이
  뜬다(`openOthersWork`). 서버도 어차피 막는다 — 모든 작품 API 가 `getWork(user.id, id)`
  로 시작해서, 내 것이 아니면 404 다. 화면은 헛걸음을 없애는 쪽이고 빗장은 서버다.
- **표지 재기** — 건너뛴다. 비율을 재도 적어 둘 곳이 내 표에 없다.
- **폴더 고르기** — 작품을 담을 때 고를 수 있는 폴더에서 빠진다. 남의 폴더에 내 것을
  넣을 수는 없다.
- **다시 공개하기** — 비추는 폴더는 `sharedView` 에서 아예 빠진다. 남에게서 받은 것을 또
  남에게 넘기면, 원래 주인이 한 사람에게만 연 것이 줄줄이 퍼진다.

### 같은 작품이 두 폴더에 걸쳐 있을 때

한 친구의 폴더를 여럿 비추고 있고 같은 작품이 그중 둘에 다 들어 있으면, 폴더마다 한 줄씩
밀어 넣던 때는 **같은 번호를 가진 줄이 둘**이 되어 「전체」와 캘린더와 검색에 겹쳐 보였다.
지금은 한 줄만 두고 `folders` 에 폴더를 보탠다 — 작품은 하나고 자리가 둘인 것이 맞다.

그리고 같은 친구의 폴더를 여럿 비추더라도 그 사람 것은 **한 번만** 읽는다. 폴더마다
`sharedView` 를 부르면 같은 질의를 폴더 수만큼 되풀이한다.

### 마지막으로 연 때는 내 것으로 바꾼다

비쳐 온 작품의 `lastAt` 은 **담긴 때(`addedAt`)로 바꿔** 넘긴다. 주인 것을 그대로 두면
친구가 무엇을 열 때마다 내 「최근 본 순」 맨 위로 튀어 오른다 — 나는 한 번도 안 본 작품인데.
담긴 때를 쓰면 "친구 목록에 새로 들어온 순" 이 되어 흔들리지 않는다. `visits` 도 0 이다.

일정은 **주인 것 그대로**다. 그것이 미러링의 뜻이고, 그래서 비친 작품도 내 캘린더에 함께 뜬다.

### 목록에서 알아볼 수 있게

내 폴더와 비추는 폴더는 폴더 탭에 **한 줄로 섞여** 있다. 그래서 폴더 이름 옆에 딱지를
달고, 거기에 **누구를 미러링하는지까지** 적는다 — `미러링 · 조예은`. 아래 작은 글씨를
읽지 않고 목록을 훑는 것만으로 남의 폴더임을 알아야 한다.

말은 화면 어디서나 **미러링**으로 통일한다 — 딱지도, 폴더 창의 `조예은님의 폴더를 미러링 중`
도, 알림의 `미러링 시작` 도. "비추다" 는 무슨 일이 일어나는지 설명하는 문장에서만 쓴다.

### 원본이 사라지면

친구가 아니게 되거나 · 공개를 거두거나 · 미러링을 꺼 버리면, 그 폴더는 **비어 있는 채로
남는다.** 말없이 지우지 않는다 — 내가 만든 줄이므로 내가 치워야 한다. 대신 폴더 줄에
왜 비어 있는지를 적는다: `이예은님 — 미러링이 꺼졌습니다`.

치우는 길은 폴더 설정의 **미러링 끊기** 다. 폴더 한 줄을 지우는 일이라, 끊어도 주인 폴더는
그대로고 내 작품이 사라질 일도 없다 — 애초에 내 표에 없었다.

여러 폴더를 한꺼번에 지울 때는 되묻는 말이 달라진다. 내 폴더는 "묶음만 사라지고 작품은
남는다" 이지만, 비추는 폴더는 **안의 작품이 원래 내 것이 아니라 함께 사라진다.**

## 함께 고치는 폴더

**폴더는 함께, 작품은 각자.** 고칠 수 있는 미러링이라고 보면 가깝다.

- 폴더에 **넣고 빼는 것**은 함께 쓰는 사람 모두 할 수 있다 — 목록을 같이 꾸린다.
- **작품 자체**(제목·일정·표지)는 넣은 사람 것이라 그 사람만 고친다.
- **남이 넣은 작품은 내 캘린더에 뜨지 않는다.** 마음에 들면 「내 목록에 담기」로 한 번 눌러
  내 것으로 만든다.

마지막 줄이 미러링과 갈리는 자리다. 미러링은 친구가 고르는 것을 **그대로 따라 보는** 일이라
그 사람 일정이 내 캘린더에 뜨는 게 맞다. 함께 고치는 폴더는 여럿이 던져 넣는 자리라, 그것이
다 뜨면 내가 보기로 한 것과 남이 넣어 둔 것이 뒤섞인다.

### 공유 폴더를 만드는 일은 한 가지 결정이다

「친구에게 공개」에 **고른 친구와 함께 쓰기** 가 있다. 이것 하나면 초대까지 나간다.

한때 공개 대상에서 `고른 친구에게만` 을 고르고 **또** 퍼가기 허용에서 `함께 고치기` 를
골라야 했다. 두 곳을 다 맞춰야 초대가 나가므로, 한 곳만 고치고는 왜 아무 일도 안 일어나는지
알 수 없었다. 화면에서는 한 항목이고 담길 때만 두 값(`share_mode='some'` + `take_mode='edit'`)
으로 갈린다. 함께 쓰는 폴더는 퍼가기가 이미 정해져 있으므로 그 칸은 아예 보여 주지 않는다.

### 한 폴더가 두 곳에 있지 않게

함께 쓰는 폴더는 **친구 폴더 보기에 나오지 않는다.** 그건 이미 참여자의 폴더 탭에 제 줄로
서 있다 — 남의 폴더를 구경하는 자리에 또 나오면 같은 폴더가 두 곳에 있는 셈이고, 어느
쪽에서 넣어야 하는지 알 수 없다.

거르는 자리는 **친구 폴더 보기 길목 하나**다. 안쪽 `sharedView` 는 그대로 둔다 —
비추는 폴더를 채우고 담아갈 것을 고르는 데 그 목록이 쓰이므로, 거기서 빼면 폴더가 통째로
비어 버린다.

### 주인이 거두어들이면

**연결이 저절로 끊기지는 않는다.** 받던 사람의 폴더 줄은 그대로 남고 비어 있게 되며, 왜인지가
적힌다(`미러링이 꺼졌습니다` · `공개가 끝났습니다`). 내가 만든 줄이므로 내가 치운다.

**다만 걸어 둔 것은 함께 걷는다.** 이게 한동안 새던 자리였다 — 주인이 함께 고치기를 꺼도
내가 걸어 둔 이음줄은 원본 폴더에 그대로 남아, 주인은 이제 남이 된 사람의 작품을 계속 보고
나는 뺄 권한이 없어 치우지도 못했다. 둘 다 손댈 수 없는 줄이 남는 셈이다.

이제 이 셋이 모두 걷어 낸다(`dropContributions`).

| 언제 | 무엇이 |
|---|---|
| 주인이 함께 고치기를 끔 | 남들이 걸어 둔 것 전부 |
| 주인이 명단에서 뺌 | 빠진 사람이 걸어 둔 것 |
| 참여자가 「함께 쓰기 그만두기」 | 내가 걸어 둔 것 |

**작품 자체는 그대로 남는다** — 빠지는 것은 이 묶음과의 이음줄뿐이다.

그리고 **거두기 전에 한 번 묻는다.** 이 설정들은 남의 화면에서 무언가를 없애는 일이라,
이름을 고치러 들어왔다가 옆 칸을 잘못 건드려 남의 폴더를 비워 버리면 되돌릴 길이 없다.

| 무엇을 바꿀 때 | 무엇을 알리나 |
|---|---|
| 함께 쓰기를 그만둘 때 | 함께 쓰던 사람이 못 보게 되고, 그 사람들이 넣어 둔 N편이 빠진다 |
| 명단에서 뺄 때 | 누구인지 이름을 대고, 그 사람이 넣어 둔 것이 빠진다 |
| 공개를 아예 거둘 때 | 보던 사람도 비추던 사람도 못 보게 된다 |
| 미러링을 끌 때 | 비추던 사람의 폴더가 빈다 (몇 명인지는 알 수 없으니 세지 않는다) |
| **볼 사람을 좁힐 때** | 미러링이 켜져 있으면, 명단에서 빠진 사람의 폴더가 빈다 |

**끊는 것은 퍼가기 설정만이 아니다.** 오래 여기 구멍이 있었다 — 「둘 다」나 「미러링만」으로
열어 둔 채 **공개 대상만** 좁히면 퍼가기 칸은 손대지 않았으니 아무 일도 없어 보이는데,
명단에서 빠진 사람의 폴더는 그 자리에서 빈다. 비추는 일이 이어지려면 **볼 수 있어야**
하므로, 볼 자격을 거두는 것도 끊는 일이다.

```
「둘 다」 · 모든 친구에게  →  「둘 다」 · 고른 친구에게만
  퍼가기 칸은 그대로 「둘 다」 — 그런데 명단에 없는 사람의 미러링은 여기서 끊긴다
```

**「담아가기만」에서는 묻지 않는다.** 담아간 사람은 이미 제 목록에 한 벌을 갖고 있어서,
내가 공개를 좁혀도 그 사람 것은 그대로다. 끊길 이음줄이 애초에 없다.

```js
/* 좁아지는가 — 이름을 댈 수 있는 것은 「고른 친구에게만」끼리 견줄 때뿐이다.
   「모든 친구에게」였다면 애초에 명단이 없어 누가 빠지는지 알 수 없다. */
const gone = was.mode === "some" && share.mode === "some"
  ? was.with.filter(id => !share.with.includes(id)) : [];
const narrowed = was.mode !== "none" &&
  (share.mode === "none" || (was.mode === "all" && share.mode !== "all") || gone.length > 0);
…
if (canMirror(take) && narrowed) …
```

넓은 것부터 묻는다 — 공개를 아예 거두는 것이 미러링만 끄는 것보다 큰 일이고, 둘이 한꺼번에
일어나면 큰 쪽을 말해 준다.

### 명단은 「공유자」 창에서 손본다

폴더 설정의 「친구에게 공개」는 명단을 **통째로 다시 쓰는** 자리다. 한 사람을 더 부르거나
한 사람만 끊는 일을 거기서 하면 손이 많이 가고, 잘못 건드리면 남은 사람까지 함께 떨어져
나간다. 그래서 폴더 안 **🤝 공유자** 창에 더하기와 끊기를 따로 뒀다.

| | 주인 | 불려 간 사람 |
|---|---|---|
| 명단 보기 | ○ | ✕ (주인 쪽에서 정한다는 안내만) |
| ＋ 더 부르기 | ○ | ✕ |
| 연결 해제 | ○ | ✕ |

**불려 간 사람에게는 두 버튼이 아예 없다.** 나가는 길은 제 폴더 줄을 지우는 것이고,
그쪽은 이미 `leaveFolder` 로 간다 — 같은 일을 하는 자리가 둘이면 어느 쪽을 눌러야
하는지 헷갈린다. 화면에서 감추는 것과 별개로 서버에서도 막는다(`mine.mirror` 면 403).

「더 부르기」는 명단을 다시 쓰지 않고 **더하기만** 한다(`inviteToFolder`). 이미 부른
사람은 고르개에 **「이미 초대됨」**으로 서고 고를 수 없다 — 목록에서 아예 빼면 "왜 이
사람이 안 보이지" 가 되고, 그냥 두면 눌렀는데 아무 일도 안 일어난다.

「모든 친구에게」 연 폴더는 명단이 없어 **한 사람만 끊을 수 없다.** 그때는 공개 대상을
먼저 좁혀야 한다고 답한다 — 조용히 아무 일도 안 하는 것보다 낫다.

### 친구 고르개는 한 물건이다

찾기 칸 · 고르개 · 담은 이름표 셋이 한 벌이고, 폴더 설정의 「고른 친구에게만」과
「공유자」 창의 「더 부르기」가 **같은 것**을 쓴다(`friendPicker`). 한때 두 벌이 따로
있었고, 한쪽만 고친 탓에 같은 창의 같은 칸이 서로 다르게 굴었다.

> **접힌 고르개에서 사람이 보는 것은 첫 줄 하나뿐이다.** 그래서 찾았으면 그 자리에
> **찾은 사람의 이름을 그대로** 보여 준다. 한때 「찾는 이름이 없습니다」를 "친 글자가
> 있으면" 띄웠는데, 그러면 제대로 쳐서 아래에 그 사람이 서 있는데도 못 찾은 줄 알았다.
> 그다음엔 「찾은 2명 중에 고르기…」로 고쳤지만, 몇 명인지 세어 주는 것보다 이름 한 줄이
> "찾았다" 는 말을 더 잘 한다.

### 부른다고 곧바로 들어오지는 않는다

이름이 올랐다고 참여자가 되지 않는다 — **수락해야** 한다(`folder_share.state`).
폴더는 아무도 수락하지 않아도 곧바로 만들어지고, 주인은 폴더 제목 옆 **🤝 공유자** 에서
누가 들어왔고 누가 아직인지 본다(`수락함` · `대기 중`). 거절하면 명단에서 사라진다.

받은 쪽은 **폴더 탭 오른쪽 아래 아이콘**으로 초대를 본다 — 캘린더의 「추가 목록」과 같은
자리다(한쪽은 캘린더에서만, 한쪽은 폴더 탭에서만 나오므로 겹치지 않는다).
**수락하면 곧바로 내 폴더 목록에 선다.** 따로 찾아 들어가 미러링을 누르게 하면 수락했는데
아무 일도 안 일어난 것처럼 보인다.

폴더 줄의 딱지가 어느 쪽인지 말해 준다 — 내가 연 것은 `공유폴더 · 오너`,
불려 간 것은 `공유폴더 · 생성자이름`.

상태의 기본값은 `ok` 다. 이 칸이 생기기 전에 공개해 둔 폴더들은 이미 보이고 있었으므로,
말없이 `pending` 으로 되돌리면 어제까지 보이던 것이 오늘 사라진다.

### 겹치면 내 것이 이긴다

친구가 넣은 작품을 나도 이미 담아 두었으면, 비쳐 온 쪽을 숨기고 **그 자리에 내 작품을 놓는다**
(같은 `platform_id + series_id`). 내 것에는 내 일정·별점·기록이 붙어 있어 실제로 다루는
쪽이고, 비쳐 온 쪽은 고칠 수도 없다. 둘 다 보이면 어느 것을 눌러야 하는지 알 수 없다.
미러링과 함께 고치는 폴더가 **같은 규칙**을 쓴다.

대체된 작품은 내 것이므로 **고칠 수 있다.** 다만 그 폴더와의 이음줄은 풀 수 없다 —
화면에서는 그 안에 있는 것처럼 보이지만 실제로 건 사람은 친구이고, **건 사람만** 풀 수 있다.
`mayFile` 이 비추는 폴더를 아예 담는 자리로 치지 않으므로, 껍데기에 이음줄이 생길 일이 없다.

### 남의 작품도 내 기록은 내 것

`visits` 와 `last_at` 은 그 작품 주인의 칸이라 내 기록을 적을 수 없다. 적었다면 친구가 열
때마다 내 목록이 흔들리고, 내가 열면 친구 목록이 흔들렸을 것이다. 보는 사람 쪽에 따로 담는다
(`work_seen`).

| | 무엇을 정하나 |
|---|---|
| `seen_at` | 눌러 봤다 — 붉은 점이 꺼진다 |
| `opened_at` | 보러 갔다 — **내 목록에서의 차례**가 된다 |

한 번도 안 갔으면 차례는 담긴 때다. 서버가 `/open` · `/seen` 을 받아 **내 작품이면 그 줄에,
남의 작품이면 내 쪽 기록에** 적는다 — 부르는 쪽은 어디에 적히는지 몰라도 된다.

### 담기 전에 무엇인지 알 수 있게

남의 작품 창(친구 폴더 · 비추는 폴더 · 공유 폴더)에 **표지와 정보**를 함께 둔다 —
플랫폼·매체·연재 일정·회차·담은 사람·담긴 때. 고칠 수는 없다. 담아 오면 내 것이 되어
그때부터 일정도 표지도 내가 정한다.

### 누가 함께 쓰는가

**"볼 수 있는 사람 = 고칠 수 있는 사람"** 이다(`folderMembers`). 볼 사람을 이미 골라
두었는데 고칠 사람을 또 고르게 하면 두 목록이 어긋날 자리가 생긴다. 그래서 새 표도,
새 설정 칸도 없다 — 퍼가기 허용을 `함께 고치기` 로 두면 그 폴더를 보는 사람들이 곧
함께 쓰는 사람이다.

### 들어오는 길은 하나

함께 쓰는 사람 쪽에서도 **비추는 폴더로 선다.** 내 목록에 남의 폴더가 들어오는 길이
하나여야 하고, 그 길은 이미 미러링이 내고 있다. 다른 것은 고칠 수 있느냐뿐이다.

### 이음줄은 원본 폴더로

내 작품을 그 폴더에 넣으면 이어지는 곳은 **원본 폴더 번호**다(`setWorkFolders` · `mayFile`).
내 쪽 비추는 폴더에 걸면 나만 보게 되므로, 주인에게도 다른 사람에게도 같은 한 곳에 담겨야 한다.

그래서 읽을 때 두 곳을 합친다.
- **주인 쪽**: 제 폴더에 남이 걸어 둔 작품을 따로 모아 온다 (`withMirrors`).
- **함께 쓰는 쪽**: 비추는 폴더를 채울 때, 원본 번호로 이어 둔 **내 작품**에 내 쪽 폴더
  번호를 하나 더 달아 준다 — 그래야 남의 것과 내 것이 한자리에 보인다.

### 담아가기도 된다

`함께 고치기` 는 담아가기와 미러링을 모두 품는 가장 너그러운 갈래다. 같이 꾸린 목록에서
마음에 드는 것을 내 것으로 만드는 일은 그 폴더의 쓰임 그대로다.

담아갈 수 있는 것을 고르는 자리도 한 곳이다(`takable`) — ① 그 사람이 나에게 연 폴더에 있고
그 폴더가 담아가기를 허락한 것, ② **내가 주인인 함께 고치는 폴더**에 그 사람이 넣어 둔 것.
②는 내 폴더라 `sharedView` 에 잡히지 않으므로 따로 모은다.

### 그만두면

「함께 쓰기 그만두기」는 내 쪽 폴더 한 줄을 지우는 일이다. 주인 폴더는 그대로고, **내가 넣어
둔 작품도 내 목록에 그대로 남는다** — 이 묶음에서만 빠진다. 주인이 폴더를 지우면
`work_folder` 가 `ON DELETE CASCADE` 로 걷혀, 남의 작품은 제 주인에게 남고 묶음만 사라진다.

## 끊겼다는 소식

미러링과 폴더 공유는 **읽을 때마다 주인 것을 가져다 보여 주는** 방식이라, 주인이 설정을
바꾸면 다음에 화면을 그릴 때 그냥 비어 버린다. 폴더 줄에 왜인지가 적히기는 하지만
**폴더를 열어 봐야** 보이므로, 자주 안 여는 폴더라면 끊긴 줄도 모르고 지낸다.

### 웹소켓을 쓰지 않는다

늘 이어 두는 길은 값이 비싸다 — 사람마다 연결 하나를 붙들고, 서버가 죽거나 되살아날
때마다 다시 이어야 하고, 프록시 너머에서는 끊기지 않게 심장 박동까지 보내야 한다.
그런데 이건 **"언젠가 알면 되는"** 소식이다. 새로 고칠 때 `/api/state` 에 함께 실려
오면 충분하고, 그 값은 이미 치르고 있던 값이다.

### 무엇이 끊길 때 남기나

| 주인이 한 일 | 남는 말 |
|---|---|
| 명단에서 뺐다 · 공개 대상을 좁혔다 | 공개가 끝났습니다 |
| 「공유자」 창에서 직접 끊었다 | 연결이 해제되었습니다 |
| 미러링을 껐다 | 미러링이 꺼졌습니다 |
| 함께 고치기를 껐다 | 함께 쓰기가 끝났습니다 |
| 폴더를 지웠다 | 폴더가 사라졌습니다 |

받을 사람은 **그때 줄이 닿아 있던 사람**이다(`connectedTo`) — 비추고 있거나, 수락하고
함께 쓰는 사람. 이름만 올라 있고 아직 수락 안 한 사람에게는 남기지 않는다: 끊길 것이
애초에 없었다.

**셈하는 자리가 중요하다.** `folder_share` 를 지우기 전에, 폴더를 지우기 전에 먼저
누가 닿아 있었는지 셈해 둔다 — 지우고 나면 물어볼 데가 없다.

```js
// setFolderShare — 지우기 전에 셈해 둔다. 넓히는 쪽(some → all)은 아무도 잃지 않는다.
const cut = mode === "all" ? []
  : connectedTo(folderId).filter(id => mode !== "some" || !viewers.includes(id));
```

폴더 이름과 주인 이름은 **그때 값으로 박아 둔다**: 폴더가 지워지면 이름을 물어볼 데가
없고, 이름이 바뀌어도 끊길 당시의 그 이름이라야 사람이 알아본다. 같은 이유로
`folder_notice.folder_id` 에는 외래키를 걸지 않았다.

### 어디서 보나

폴더 탭의 **🤝** 는 이제 「폴더 알림」이다. 안에 두 갈래가 있다.

```
🤝 폴더 알림
   ✉️ 폴더 초대  3    수락하면 그 폴더가 내 목록에 함께 섭니다.   ›
   🔗 알림       2    끊긴 폴더가 있습니다.                      ›
```

성격이 반대라 한 목록에 섞지 않는다 — 들어오라는 것과 끊겼다는 것을 나란히 두면
수락 버튼 옆에 끊긴 소식이 선다. 갈래를 고르면 그쪽만 펼쳐지고, 머리줄의 **‹** 로
돌아온다. 붉은 숫자는 **초대 + 안 읽은 소식**이다.

「알림」을 여는 순간 읽음으로 둔다 — 붉은 숫자가 세는 것은 "봤나" 이지 "치웠나" 가
아니다. 읽은 줄도 치우기 전에는 남아 있고, 아직 안 본 줄에는 왼쪽에 붉은 띠가 선다.

## 폴더 공유

폴더마다 **누구에게 보일지**를 정한다. 세 갈래다.

| `share_mode` | 뜻 |
|---|---|
| `none` | 나만 본다 (기본) |
| `all` | 모든 친구에게. 친구가 늘어나면 그 사람에게도 보인다 |
| `some` | 고른 친구에게만. 짝은 `folder_share(folder_id, viewer_id)` 에 담는다 |

담아 둔 것 전부가 아니라 **폴더 단위**로 연다. 한때 켬/끔 둘뿐이었는데, "이 친구에게만"
이 필요해져 세 갈래로 늘렸다. 옛 `shared` 열은 시작할 때 `all` 로 옮기고 더는 읽지 않는다.

**보는 사람에 따라 결과가 다르다** — `sharedView(owner, viewer)`. 같은 주인의 폴더라도
누가 물었느냐에 따라 목록이 달라진다. 친구 목록의 "폴더 N개" 도 그 친구가 연 폴더 수가 아니라
**나에게 보이는** 수다.

공개 대상은 저장하는 쪽에서 **실제 친구인지 확인하고 거른다.** 친구가 아닌 사람의 아이디를
끼워 넣어도 담기지 않는다 — 지우는 쪽이 아니라 담는 쪽에서 막아야 새는 곳이 없다.

## 친구 폴더 보기

폴더 탭 맨 위에 **지금 누구의 폴더를 보고 있는지**가 있다. 내 것이면 `내 폴더`,
친구 것이면 `현재 폴더: 영수` 와 함께 **`내 폴더`(왼쪽) · `다른 친구 폴더`(오른쪽)** 가 나온다 —
돌아가는 길이 왼쪽, 더 나가는 길이 오른쪽으로, 읽는 차례와 같다. **색은 나가는 쪽에만** 준다 —
`내 폴더` 는 되돌아오는 길이라 눈에 띌 것 없이 늘 같은 자리에 있으면 된다.
`다른 친구 폴더`(또는 내 폴더일 때의 `친구 폴더 보기`)를 누르면 친구 목록이 팝업으로 뜨고,
고르면 그 사람이 **나에게** 공개한 폴더가 폴더 탭에 그대로 들어온다.

그 목록에는 **볼 수 있는 사람만** 나온다 — 나에게 공개한 폴더가 없는 친구는 눌러도 빈 화면이라
둘 이유가 없다. `내 폴더` 줄도 두지 않는다: 돌아가는 길은 머리줄의 `내 폴더` 버튼이고,
같은 일을 하는 자리가 둘이면 어느 쪽을 눌러야 하는지 헷갈린다.
친구가 넷을 넘으면 이름으로 찾는 칸이 함께 나온다.

친구 폴더는 **보기만 한다.** 고치거나 지우는 것은 주인만 할 수 있어서 `⋮` 도 `＋ 새 폴더` 도
없다.

안의 작품을 누르면 **작품 창**이 폴더 위에 겹쳐 뜬다 — 제목, 어느 플랫폼인지, `보러가기`,
그리고 `내 목록에 담기`. 내 작품을 눌렀을 때와 같은 모양이라 새로 익힐 것이 없다.

한때 줄을 누르면 곧바로 담기 화면이 열렸다. 친구 폴더를 훑는 일은 대개 "뭘 보나" 구경하는
것이지 곧바로 담는 것이 아닌데, **들여다볼 자리가 아예 없었다.** 게다가 주소 없이 담은
항목(직접 입력한 것)은 담을 수도 없는데 빈 담기 창이 떠서 고장처럼 보였다. 지금은 그런
항목이면 담기 버튼 대신 왜 담을 수 없는지를 적어 둔다.

## 가져가는 두 가지 방식

친구가 공개한 폴더를 내 것으로 만드는 길은 둘이고, **서로 다른 물건**이다.

| | 담아가기 | 미러링 | 함께 고치기 |
|---|---|---|---|
| 내 표에 남는 것 | 폴더 한 줄 + **작품 한 벌** | 폴더 **한 줄만** | 폴더 한 줄 + **내가 넣은 것** |
| 폴더에 넣고 빼기 | 내 폴더니 마음대로 | 못 한다 | **할 수 있다** |
| 남이 넣은 작품 | — | 고칠 수 없다 | 고칠 수 없다 |
| 친구가 고치면 | 안 바뀐다 | **같이 바뀐다** | **같이 바뀐다** |
| 남의 것이 내 캘린더에 | — | **뜬다** | **안 뜬다** |
| 코드 안 이름 | `copy` | `mirror` | `edit` |

담아가기는 **사진을 찍는 것**이고 미러링은 **창을 내는 것**이다. 어느 쪽이 맞는지는
상황이 정한다 — "친구가 추천한 걸 내 목록에 넣고 내 일정으로 관리하겠다" 면 담아가기,
"친구가 고르는 걸 계속 따라 보겠다" 면 미러링이다.

## 퍼가기 허용

**보는 것과 가져가는 것은 다른 일이다.** 공개했다고 퍼 가도 좋다는 뜻은 아니어서,
폴더마다 `folder.take_mode` 로 정한다 — `none`(보기만) · `copy` · `mirror` · `both`.
폴더 설정에서 **공개 대상을 정했을 때만** 이 칸이 나타난다. 아무에게도 안 보이는 폴더에
퍼가기라는 말은 성립하지 않는다.

**새 폴더를 만들 때도 함께 정한다.** 한때 만든 뒤에 다시 열어 고쳐야 했는데, 공유하려고
만드는 폴더라면 그 자리에서 정하는 것이 자연스럽다. 만들기와 고치기가 같은 값을 보내므로
서버도 받아들이는 잣대를 한 곳에 둔다(`applyShare`).

### 고른 친구는 하나씩 담는다

"고른 친구에게만" 을 골랐을 때, 한때 **모든 친구를 이름 칩으로 깔아 두고** 눌러서 켜고 껐다.
수십 명이 되면 그것만으로 화면이 가득 차서 정작 아래에 있는 퍼가기 설정이 안 보였다.

지금은 **고르개(select)로 하나씩 담는다.** 고른 이름이 아래에 붙고, 그 이름을 누르면 빠진다.
보이는 길이가 고른 수만큼이라 몇 명을 담아도 화면이 늘어나지 않는다.

고르개에는 **아직 안 담은 사람만** 올린다 — 이미 담은 이름이 남아 있으면 골랐을 때 아무 일도
안 일어나는 것처럼 보인다. 친구 목록은 그때 처음 불러온다(「친구가 많아지면」).

> **치는 칸은 다시 그리지 않는다.** 이 찾기 칸을 한때 글자마다 통째로 다시 그렸는데,
> 그러면 치는 도중에 칸이 사라졌다 새로 생겨서 **한글처럼 모아 쓰는 글자가 깨진다** —
> 초성을 치는 순간 조합하던 칸이 없어지니 이어 붙을 자리가 없다. 커서를 되돌려 놓는
> 것으로는 못 막는다. 갈아 끼우는 것은 아래 목록뿐이어야 한다.

> **안내말은 찾은 결과를 보고 정한다.** 한때 "친 글자가 있으면 못 찾은 것" 으로 쳤는데,
> 그러면 이름을 제대로 쳐서 목록에 그 사람이 서 있는데도 고르개에는 「찾는 이름이 없습니다」가
> 적혀 있었다. **접힌 고르개에서 사람이 보는 것은 이 한 줄뿐**이라, 찾아 놓고도 못 찾은
> 줄 알았다. 세 갈래로 가른다 — 찾은 것이 있으면 몇 명인지, 쳤는데 없으면 없다고,
> 안 쳤는데 없으면 모두 골랐다고.

친구가 여덟을 넘으면 고르개 위에 **좁히는 칸**을 둔다. 고르개를 열어 놓고 굴리는 동안에는
눈으로 훑는 것 말고 할 수 있는 게 없어서, 몇 글자 치면 그만큼 짧아지게 했다. 하나 담으면
찾던 글자는 지운다 — 다음 사람을 찾을 차례이기 때문이다.

고르는 줄과 고르개 사이는 띄운다(`14px`). 붙어 있으면 고르개가 어느 쪽에 딸린 것인지 흐리다.

기본값은 `copy` 다. 이 칸이 생기기 전에는 공개한 폴더를 담아갈 수 있었으므로, 말없이
막아 버리면 어제까지 되던 것이 오늘 안 된다. **미러링은 새로 생긴 것이라 주인이 직접
켜야 열린다** — "내가 고르는 걸 계속 보라" 는 뜻이라, 모르는 사이에 켜져 있으면 곤란하다.

허락하지 않은 길은 **버튼을 아예 두지 않는다.** 눌러 봐야 막히는 버튼을 띄우느니 없는
편이 낫다. 그리고 서버가 같은 잣대로 한 번 더 거른다 — 화면이 유일한 빗장이면 빗장이 아니다.

작품 **한 편**은 그것이 들어 있는 폴더 중 **하나라도** 담아가기를 허락하면 담을 수 있다.
한 작품이 여러 폴더에 들어 있을 수 있고, 그중 하나라도 열어 뒀다면 주인이 그 작품을
가져가도 좋다고 한 것이다.

## 담아가기

친구 것을 **내 것으로 한 벌 떠 온다.** 떠 온 뒤로는 서로 상관이 없다 — 내가 고쳐도 친구
것은 그대로고, 친구가 고쳐도 내 것은 그대로다. 작품 한 편(`내 목록에 담기`)도, 폴더 통째
(`담아가기`)도 같은 방식이다.

### 다시 읽지 않는다

담기를 누르면 **그 자리에서 담긴다.** 한때 URL 추가 창으로 넘겨서 서버가 그 페이지를 다시
읽게 했는데, 친구 쪽에 제목·표지·플랫폼·일정이 **이미 다 있는데도** 그랬다. 게다가 CGV·
카카오페이지처럼 읽기를 막는 곳이면(「못 읽는 곳과 안 내놓는 곳」) 친구는 멀쩡히 갖고 있는
표지를 나는 못 받았다. 친구 것을 그대로 떠 오는 편이 빠르고 결과도 낫다.

### 무엇을 베끼고 무엇을 두고 오는가

잣대는 하나다 — **그 작품에 대한 것은 베끼고, 그 사람과 작품 사이의 것은 두고 온다.**

| 베낀다 | 두고 온다 |
|---|---|
| 제목 · 표지 · 플랫폼 · 주소 · 연재 일정 | 별점 · 본 횟수 · 마지막으로 연 때 · 캘린더 점 색 |

뒤쪽까지 따라오면 내가 보지도 않은 작품에 남의 기록이 붙는다. 담아온 것은 늘 **오늘 담은,
아직 한 번도 안 본 작품**으로 시작한다.

**표지 파일은 따로 한 장 뜬다.** 친구가 올린 그림은 `/covers/<친구작품id>.jpg` 인데,
주소만 베끼면 친구가 그 작품을 지울 때 파일도 함께 지워져 내 표지가 깨진다. 바깥 사이트의
그림 주소면 그대로 쓴다 — 그건 원래 남의 서버에 있는 것이다.

### 이미 갖고 있는 것

같은 작품(`platform_id` + `series_id`)을 이미 담아 뒀으면 **새로 만들지 않는다.**
한 편만 담을 때는 "이미 담겨 있습니다" 로 알리고 끝내고, 폴더째 담을 때는 **갖고 있던 그
작품을 새 폴더에 함께 넣는다** — 같은 것이 둘로 늘지 않는다. 알림에 몇 편이 새로 담기고
몇 편이 이미 있던 것인지 함께 적는다.

내 것은 손대지 않는다. 제목을 내가 고쳐 뒀을 수도 있고, 보관함에 내려둔 것을 말없이
되살릴 일도 아니다.

### 볼 수 있는 것만

담아갈 수 있는 것은 **친구가 나에게 공개한 폴더 안**뿐이다. 무엇이 보이는지는 `sharedView`
가 이미 알고 있으므로, 서버는 거기 없는 번호를 달라고 하면 그냥 없다고 답한다 — 작품 번호를
넣어 보며 남의 목록을 더듬는 길이 열리지 않는다.

보고 있는 친구는 화면에만 있고 주소에는 남기지 않는다. 새로 고치면 늘 내 폴더로 돌아온다 —
남의 목록에 머물러 있는 편보다 내 것부터 보이는 편이 낫다.

친구 화면(왼쪽 메뉴 → 친구 → 한 사람)에서도 `폴더 보러 가기` 로 같은 자리에 닿는다.
한때 그 화면이 공개 폴더를 통째로 한 벌 더 그렸는데, 같은 것을 두 곳에서 그리면 한쪽만
고치는 일이 생겨 걷어냈다. 거기 남은 것은 신원과 `친구 끊기` 뿐이다.

## 되풀이를 한 자리로

같은 모양이 세 번 넘게 나오면 자리를 하나 만든다. 지금 그렇게 묶여 있는 것들:

| 자리 | 무엇 | 쓰는 곳 |
|---|---|---|
| `folderRows(where, ...)` | 폴더 읽기 | `listFolders` · `getFolder` |

바꿔 `getFolder` 를 낸 이유다.

## 값 점검 — 무엇이 비쌌나

한 번 훑고 잰 결과를 적어 둔다. **재 보기 전에는 어디가 비싼지 알 수 없었다** — 짐작으로
고친 것 중 실제로 값이 나간 것은 절반뿐이었다.

### 폴더에서 되짚는 길에 색인이 없었다

`work_folder` 의 기본키는 `(work_id, folder_id)` 다. 그래서 **작품에서 폴더로** 가는 길만
나 있었는데, 정작 자주 묻는 것은 반대쪽이다 — "이 폴더에 무엇이 들어 있나". 비추는 폴더,
함께 쓰는 폴더, 담아갈 것 고르기가 전부 그 길로 다닌다.

```
EXPLAIN QUERY PLAN
  SELECT w.* FROM work w JOIN work_folder wf ON wf.work_id = w.id WHERE wf.folder_id = ?

  전:  SCAN wf                                   ← 표를 통째로 훑는다
  후:  SEARCH wf USING INDEX idx_wf_folder (folder_id=?)
```

`folder_share` 도 같았다. 기본키가 `(folder_id, viewer_id)` 인데 "나에게 온 초대" 는
`viewer_id` 로 묻고, 그건 **앱을 열 때마다** 도는 질의다.

### 한 편 읽자고 질의를 셋씩 썼다

함께 쓰는 폴더에서 남이 걸어 둔 작품을 모으는 자리가 이랬다.

```js
const rows = db.prepare("SELECT w.*, u.display_name … WHERE wf.folder_id = ?").all(f.id, me);
for (const r of rows) {
  const w = getWork(r.user_id, r.id);   // ← 작품 한 줄 + 그 폴더 목록, 질의 두 번 더
  …
  works.push(asGuest(w, f.id, …));      // ← 그 폴더 목록은 여기서 곧바로 덮어쓴다
}
```

첫 질의가 **이미 줄 전체를 들고 있는데** 번호만 쓰고 다시 물었다. 게다가 그렇게 얻어 온
폴더 목록은 `asGuest` 가 `folders: [folderId]` 로 갈아 끼워 온전히 버려졌다. 헛일을 두 번
한 셈이다. `contributedWorks(folderId, {not: me})` 로 한 질의에 끝낸다.

| 남이 30편을 걸어 둔 폴더 | 걸린 때 | 질의 |
|---|---|---|
| 전 | 5.27ms | 61번 |
| 후 | 0.50ms | 1번 |

담아갈 것을 고르는 `takable` 에도 같은 모양이 있어 함께 고쳤다.

### 같은 문장을 요청마다 다시 컴파일했다

`db.prepare` 는 부를 때마다 SQL 을 새로 컴파일한다 — 한 번에 0.1ms 남짓인데, 우리는 같은
문장을 요청마다 되풀이해 부르므로 그것만으로 질의 값의 3분의 1을 썼다. 한 번 만든 것을
글자 그대로 기억해 두었다가 다시 쓴다.

**놓는 자리가 중요하다.** 켤 때 도는 `ALTER TABLE` 이 다 끝난 뒤여야 한다 — 기억해 둔
`SELECT *` 는 준비하던 때의 칸만 알기 때문에, 칸이 늘기 전에 만든 문장을 그대로 쓰면 새
칸이 빠진다. 스키마가 자리를 잡고 나면 그 뒤로는 바뀌지 않으므로 그때 걸어 둔다.

### 정적 파일을 부를 때마다 디스크에서 읽었다

`app.js` 만 160KB 다. 사람이 앱을 한 번 열 때마다 `stat` 하고 `readFile` 하고 있었는데,
그 파일들은 이미지에 구워져 있어 도는 동안 바뀌지 않는다. 판 번호(`assetV`)를 한 번만
셈하는 것과 같은 이치로 내용도 한 번만 읽어 들고 있는다. `index.html` 은 판 번호를 박아
넣은 뒤의 모습으로 갈무리한다 — 그 치환도 매번 할 일이 아니다.

### 잰 값

| 하는 일 | 전 | 후 |
|---|---|---|
| `listWorks` + `listFolders` | 0.82ms | 0.57ms |
| `listFriends` (친구 200명) | 1.44ms | 1.20ms |
| `sharedView` (친구 폴더 보기) | 0.88ms | 0.35ms |
| 남이 걸어 둔 30편 읽기 | 5.27ms / 61질의 | 0.50ms / 1질의 |

**HTTP 왕복으로 재면 아무 차이도 안 보인다.** 되돌아오는 데만 13ms 가 드는데 서버가 하는
일은 1ms 아래라, 지금 규모에서 이 손질은 사람 눈에 띄지 않는다. 그래도 해 둔 이유는 값이
**폴더에 든 편수를 따라 늘어나는** 자리들이라서다 — 표를 통째로 훑는 질의와 한 편에 질의
셋은 지금 안 아플 뿐이지 나중에 아프다.

### 켤 때 한 번이면 되는 일

옛 자료를 손보는 조각들이 표식 없이 놓여 있어 **켤 때마다 다시 돌았다** — 작품 표를 훑고,
주소를 하나씩 뜯어보고, 고칠 것이 없다는 결론을 매번 새로 냈다. DB 자체의 판 번호를 표식
삼는 `once(n, fn)` 으로 묶어, 지나간 것은 건너뛴다.

```js
once(5, restoreHostGrouping);   // 주소를 한 줄씩 뜯어보는 일이라 가장 비쌌다
```

지금 자료(작품 508편)에서는 켜는 때가 눈에 띄게 줄지 않았다. 이건 값보다 **틀**의 문제다 —
한 번이면 되는 일에 표식을 달아 두지 않으면 자료가 늘수록 켜는 값이 조용히 자란다.

### 친구 목록에 적힌 폴더 수가 실제와 달랐다

값이 아니라 **어긋남**이다. 친구 목록의 "폴더 3개" 는 그 친구가 공개한 폴더를 세는데,
막상 눌러 들어가면 그중 일부가 빠진 목록이 나왔다. 세는 조건과 보여 주는 조건이 따로
자란 탓이다.

| | 세던 쪽 | 보여 주던 쪽 |
|---|---|---|
| 고른 친구에게만 | 짝이 있는 사람만 ✓ | 짝이 있는 사람만 ✓ |
| 비추고 있는 폴더 | 셌다 ✗ | 안 보여 준다 |
| 함께 쓰는 폴더 | 셌다 ✗ | 안 보여 준다 |

세는 쪽에 `mirror_folder IS NULL AND take_mode <> 'edit'` 을 더해 맞췄다. 고친 뒤
계정 166명의 응답 501건을 전후로 맞대 보니 **딱 이 한 자리만 달라졌다** (5 → 4).

## 앱으로 열기

**내 작품이든 남의 것이든 여는 방식은 같다.** 한때 남의 작품 창(친구 폴더 · 비추는 폴더)은
웹 주소만 걸어 두어서, 설정에서 "앱으로" 를 골라 두었어도 미러링해 온 목록에서는 늘
브라우저가 떴다. 같은 일을 두 자리에서 따로 적어 두었으니 한쪽만 고쳐진 것이다 —
지금은 `goHtml` · `wireGo` 한 벌을 두 창이 함께 쓴다.

다른 것은 하나뿐이다: **접속 기록은 내 작품일 때만 남긴다**(`wireGo(w, count)`).
남의 작품에 내가 몇 번 열었는지를 적을 자리는 없다.

작품을 열 때 플랫폼 앱이 있으면 앱으로 넘긴다. 앱 주소는 플랫폼마다 다른 사설 스킴이라
`platforms.ts` 에 적어 두는데, **짐작으로 적으면 아무 데도 안 간다.** 네이버웹툰이 그랬다 —
`naverwebtoon://` 로 적어 두었지만 실제로 네이버가 자기 모바일 페이지(`m.comic.naver.com`)
에서 쓰는 것은 `webtoonkr://contentList?version=2&league=WEBTOON&titleId=…` 이었다.
이미 담긴 작품의 주소도 시작할 때 한 번 고쳐 준다.

앱이 없으면 아무 일도 일어나지 않으므로 잠시 뒤 웹으로 넘긴다. 그런데 이 타이머가 앱이
**떴을 때도** 돌아서, 앱으로 갔는데 웹까지 열리는 일이 있었다. 넘기기 직전에 세 가지를 본다.

1. **화면이 가려졌는가** (`document.hidden`) — 앱이 떠 있다는 뜻이다.
2. **포커스가 있는가** (`document.hasFocus()`) — 사파리는 사설 주소를 열기 전에
   "…앱을 여시겠습니까?" 를 묻는다. 그 창이 떠 있는 동안 문서는 포커스를 잃는다.
   묻는 중에 웹으로 넘겨 버리면 물음창째로 사라진다.
3. **타이머가 밀렸는가** — 앱에 다녀오는 동안 타이머는 멈춰 있다가 돌아온 뒤 뒤늦게 터진다.
   잰 시간이 정한 것보다 한참 지났으면 이미 앱에 다녀온 것이다.

셋 중 하나라도 걸리면 넘기지 않는다. 애매할 때 **안 넘기는 쪽**을 고른 것이다 — 앱으로 잘 갔는데
웹이 덮어쓰는 쪽이, 앱이 없을 때 그냥 가만히 있는 쪽보다 나쁘다. 웹으로만 열고 싶으면
설정에서 "웹으로 열기" 를 고르면 된다.

모바일에서는 `window.open` 을 쓸 수 없다 — 사파리는 사용자가 누른 직후가 아닌
`window.open` 을 팝업으로 막아서, 타이머 안에서 부르면 아무 데도 못 간다. 이 창을 그대로 옮긴다.

나머지 플랫폼의 스킴은 실기기로 확인하지 못했다. 안 열리는 곳이 있으면 그 사이트의 모바일
페이지가 쓰는 값을 보고 고치면 된다 — 짐작하지 않는 것이 요령이다.

## 배포해도 옛 화면이 그대로일 때

정적 파일에는 `Cache-Control: no-cache` 를 붙여 보낸다. 그런데 앞에 선 **Cloudflare 가 그걸
무시하고** 브라우저에 `max-age=14400` — "4시간 동안 다시 묻지 말라" — 로 고쳐 보낸다.
무료 요금제의 기본값이라 원본 헤더로는 못 끈다. 그래서 배포를 해도 기기가 옛 `app.js` 를
계속 쓰고, 화면이 그대로였다.

**주소 자체를 바꾼다.** 파일 내용에서 판 번호를 만들어 `/app.js?v=f51ac86c` 로 부른다.
내용이 바뀌면 주소가 바뀌므로 캐시에 있을 수가 없다. `index.html` 은 Cloudflare 가 캐시하지
않는 문서(`cf-cache-status: DYNAMIC`)라 늘 새 판 번호를 들고 온다. 판 번호는 시작할 때 한 번
계산한다 — 파일은 이미지에 구워져 있어 도는 중에 바뀌지 않는다.

서비스 워커의 미리받기 목록에서도 두 파일을 뺐다. 판 번호가 붙은 주소로 불리므로, 맨주소를
미리 받아 두면 쓰이지도 않을 옛 파일만 쥐고 있게 된다. 실제로 불린 주소는 `fetch` 가
그때그때 담으므로 오프라인에서도 열린다.

Cloudflare 대시보드에서 **Caching → Browser Cache TTL** 을 "Respect Existing Headers" 로
바꾸면 원본 헤더가 살아난다. 그래도 판 번호는 그대로 두는 편이 낫다 — 그쪽 설정에 기대지 않고
배포마다 확실히 새 파일이 간다.

## 알려진 한계

- **격주·비정기 연재** — 플랫폼 표기가 주 단위뿐이라 표현할 방법이 없다.
- **시간대** — 요일 계산은 서버/브라우저 로컬 시간을 쓴다. KST 밖에 배포하면 자정 근처에서
  하루 밀린다. `Asia/Seoul` 고정이 필요하다.
- **연재 요일 수동 입력** — 자동으로 채울 방법이 정당하게는 없다. 대신 휴재를 알 수 없어
  쉬는 주에도 캘린더가 "오늘 업데이트"라고 말한다.
- **OG 품질은 사이트 마음** — 카카오페이지처럼 작품별 정보 없이 사이트 이름만 내놓는 곳이 있다.
- **HTTPS 전제** — 쿠키의 `Secure` 는 `BASE_URL` 이 https 일 때만 붙는다. 공개 배포 시 반드시 https.
- **자격 증명 미설정 시 무인증** — 로컬 계정으로 누구나 접근한다. 로컬에서만 그렇게 띄울 것.
